# 宗祠祭祀 / 消费记录 —— 消费人名称展示

> 需求：宗祠祭祀的消费记录要能看出「是谁献祭的」，但公开页面又不能泄露个人隐私。

## 一、最终决策

| 议题 | 决策 |
|---|---|
| 记录范围 | 免费祭品 + 积分供奉（现金供奉走商城下单，不在此处） |
| 名称展示 | **实名但脱敏**——按真实姓名打码，不是匿名编号 |
| 可见性 | **馆主看完整实名 + 联系方式；前台只看脱敏名号** |
| 交互风格 | 不做动效与音效，庄重简洁 |

## 二、脱敏规则（`lib/mask.ts`）

优先级：**真实姓名 > 手机号 > 邮箱 > 「匿名宗亲」**

| 输入 | 输出 |
|---|---|
| 张三（2 字） | 张* |
| 李明华（3 字） | 李*华 |
| 欧阳明华（4 字） | 欧**华 |
| 爱新觉罗溥仪（6 字） | 爱****仪 |
| John（拉丁） | J*** |
| 13812345678 | 138****5678 |
| user@test.com | us***@test.com |
| 全部为空 | 匿名宗亲 |

> 设计要点：**任何情况下都不产生空白**，避免出现「只有图标没有名字」的记录。
> 4 字及以上保留首尾、中间全码，兼容复姓（欧阳、司马、爱新觉罗）。

## 三、数据模型

新增 `ClanTribute`（与纪念馆的 `MemorialTribute` 分表，因语义与字段需求不同）：

```prisma
model ClanTribute {
  id           String           @id @default(cuid())
  clanHallId   String
  userId       String?
  productId    String?
  type         ClanOfferingType @default(incense)
  displayName  String   // 脱敏名号（前台唯一可见的字段）
  realNameSnap String?  // 完整实名快照（仅馆主）
  contactSnap  String?  // 完整联系方式快照（仅馆主）
  amountFen    Int      @default(0)  // 现金恒为 0
  pointsCost   Int      @default(0)
  message      String?
  createdAt    DateTime @default(now())
}
```

### 为什么用「快照」而不是联表实时取

记录写入时**冻结**当时的身份值。用户日后补改实名，**不会**回溯改写历史记录——
避免同一批历史记录的身份随用户资料变动而漂移（这会破坏审计可信度）。

> 这正是测试时「先改实名再查旧记录，看到的仍是旧值」的原因，是**有意设计**。

## 四、安全设计

1. **前台查询只 `select displayName`**，服务端从不把 `realNameSnap` / `contactSnap` 送进前台组件的 props。
2. **`amountFen` 恒为 0**，金额绝不从前端接收——从根上杜绝伪造金额入账；现金供奉一律走商城下单流程。
3. 写入前二次校验 `ClanHall.status === 'active'` 与 `Product.status === 'active'`。

## 五、防刷规则

| 规则 | 值 |
|---|---|
| 同一用户对同一祭品冷却 | 30 秒 |
| 免费祭品每日每宗祠上限 | 30 次 |
| 免费献祭奖励 | +2 积分（与纪念馆祭拜一致） |

两层防刷分别针对「误触重复提交」与「刷榜刷积分」。

### 公网泄露实时检查（最关键的断言）

对公网 HTML 全文 grep，完整实名与手机号出现次数：

```
李明华 → 0    张三 → 0    欧阳明华 → 0
13812345678 → 0    13900001111 → 0    13712345678 → 0
```

脱敏名号出现次数（正常渲染）：`李*华` 2、`张*` 2、`欧**华` 2、`us***@test.com` 2

**结论：前沿公开展示面零实名泄露。**

## 八、纪念馆追思记录：同一套脱敏（2026-09 补修）

**缺陷**：宗祠侧做完脱敏后，**纪念馆侧漏了**。`MemorialTribute` 当时没有身份快照字段，
前台为了显示"是谁献祭的"，只能 `include: { user: { select: { realName: true } } }` 并**原样渲染** ——
于是**任何访客**打开纪念馆都能看到献祭者的完整真实姓名（连登录都不需要）。

这在代码里长这样（修复前）：

```ts
prisma.memorialTribute.findMany({
  include: { user: { select: { realName: true } } },   // ← 拿到完整实名
})
// …
{t.user?.realName ? ` · ${t.user.realName}` : ""}      // ← 原样渲染到公网页面
```

**修法**：把纪念馆拉到与宗祠**完全相同的口径**，而不是"渲染时记得打码"。

1. **加字段**（迁移 `20260930120000_add_memorial_tribute_identity`）：
   `MemorialTribute` 增加 `displayName` / `realNameSnap` / `contactSnap`，与 `ClanTribute` 对齐。
   `displayName` 的 DB 默认值是 `'匿名宗亲'` —— 与 `lib/mask.ts` 的兜底文案**必须一致**，
   否则同一套规则在纪念馆显示「匿名亲友」、在宗祠显示「匿名宗亲」，看起来像两个系统。
2. **历史回填**：89 条旧记录全部回填，**0 条空名**。
   回填在 SQL 里复刻了 `lib/mask.ts` 的规则；为避免多字节姓名被切坏，
   一律用 PostgreSQL 的**字符语义**（`LEFT/RIGHT/CHAR_LENGTH`，不是字节的 `SUBSTRING`）。
   已逐条与 JS 的 `maskIdentity()` 比对：**89/89 零不一致**。
3. **写入冻结**：抽 `identitySnapshot(userId)` 公共函数，免费献祭 / 收费祭拜 / 留言**三条写路径共用**，
   保证口径唯一。写入时冻结还顺带避免了"用户日后改实名 → 历史记录身份漂移"。
4. **查询层杜绝**：前台 `select` 改成显式 `displayName`，**不再 include 活用户表**。
   这不是"记得打码"的约定，而是从查询层就拿不到实名 —— 想泄露都没有数据源。

**验收**：`scripts/verify-memorial-tribute-mask.mjs`，**21 项断言**。含三条源码级回归防护
（不得再出现 `include: { user:`、不得 select `realName`、必须显式 select `displayName`）。

### 一条方法论：断言必须做反向验证

上面"前台不含完整实名"这类断言，写法是 `!html.includes(实名)`。
它有个隐蔽问题：**页面没渲染记录时也返回 `true`** —— 看着通过，其实什么都没测。

本次特意做了一次**反向实验**：临时把前台改回旧写法（include user + 渲染 realName），
重跑套件 → **6 条断言全部变红**，其中核心那条明确报出 `出现「欧阳明华」`；
还原后立刻回到 21/21。这才算证明断言"真的能抓到泄露"。

> 同类坑见 `AGENTS.md`：别用 `indexOf(...) < indexOf(...)` 那种"数据为空则恒真"的写法。

### 顺带发现：族谱「收录者」也有同样问题（未修，待确认）

`app/(public)/clan/genealogy/[id]/page.tsx:122` 渲染 `g.owner?.realName`（完整实名），
数据侧确认存在普通用户实名被公开展示（如 `黄氏/江夏堂 → 李明华 / user`）。
另 `app/(public)/clan/community/page.tsx:78,89` 用 `realName.slice(0,1) + "宗亲"`（近似脱敏，但口径不统一）。
