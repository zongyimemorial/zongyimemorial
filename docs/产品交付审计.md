# 产品交付审计（2026-10）

> 任务：重新梳理平台产品体系，核查「支付/兑换后是否真的能交付给用户」。
> 结论：**实体商品、虚拟商品、装修、订阅、存储、福币、电子讣告均闭环；审计时另有 7 个在售商品付了钱/积分却什么都拿不到**（云祭扫 1 个 + 非讣告纪念服务 6 个），与最初的「电子讣告发布」bug 同源。
> **处置状态（2026-10）：已按方案甲补齐「服务受理体系」，7 个商品全部闭环，详见第 4 节。**

---

## 1. 审计方法

逐条追踪两条「支付」路径的履约代码，并与 DB 在售商品交叉比对：

| 路径 | 履约代码 | 说明 |
|---|---|---|
| 现金/模拟支付 | `lib/pay.ts` → `simulatePay` | 订单 `paid` 后按 `item.product.type` 分支逐类发放权益 |
| 积分兑换 | `app/(public)/points/actions.ts` → `redeemItem` | 扣积分后按 `product.type` 分支发放；无分支则**扣完即写 `done`，不交付任何东西** |
| 实体发货 | `app/admin/orders` + `lib/orders.ts` | 带收货地址的订单 → `shipStatus=pending` → 后台「标记发货」 |

数据基准：DB 共 **11 个 ProductType、137 个在售商品**（inactive 不计入，因无法下单）。

## 3. 断裂清单（付了钱却什么都拿不到）

### A. 云祭扫服务 `cloud_worship`（1 个）

| 商品 | 现金价 | 积分价 |
|---|---:|---:|
| 云祭扫服务 | ¥39 | 5850 |

- `simulatePay` **无 `cloud_worship` 分支** → 支付后无副作用。
- `redeemItem` **无分支** → 兑换会扣 5850 积分、写 `status=done`，但**什么都没发放**（白扣积分）。
- 全仓唯一出现的 `cloud_worship` 是种子数据、管理后台、商品展示、积分页展示——**没有任何受理/履约逻辑**。
- 无「提交祭扫需求」入口、无后台工单、无用户侧状态页。

### B. 纪念服务（非讣告）`memorial_service`（6 个）

| 商品 | 现金价 | 积分价 | 性质 |
|---|---:|---:|---|
| 生平传记代写 `bio-writing` | ¥198 | 39600 | 人工文案（需资料收集） |
| 纪念馆首页风格定制 `homepage-style` | ¥30 | 3000 | 人工/样式 |
| 追思纪念视频制作 `memorial-video` | ¥88 | 13200 | 人工视频（需素材） |
| 线上追思会（直播）`online-memorial-meeting` | ¥128 | 19200 | 人工直播（需排期） |
| 扫码云碑（二维码铭牌）`qr-tombstone` | ¥49 | 7350 | 实物+上链（需寄送） |
| 墓碑样式更换 `tombstone-style` | ¥15 | 1500 | 样式 |

- `simulatePay` 对 `memorial_service` **只接了 `slug === "e-obituary"`**（`lib/pay.ts:274`），其余 6 个穿透无副作用。
- `redeemItem` 同样只接 `e-obituary`（`app/(public)/points/actions.ts:128`）→ 这 6 个积分兑换全部**白扣积分**。
- 种子文案 `prisma/seed-content.mjs` 明确描述人工交付（「交付初稿」「我们协助流程设计」），说明本**设计意图是人工服务**，但**没有任何受理入口、后台工单、用户提交资料/查看进度的页面**。
- 商品页 `app/(public)/mall/[slug]/page.tsx` 只对 `e-obituary` 写了「购买后如何发布」提示，这 6 个服务**既无提示也无入口**。

### C. 边缘：午夜悄悄话 `whisper-clone` 静默 no-op

`simulatePay` 的克隆分支（`lib/pay.ts:211`）**仅当用户已存在 `whisperProfile` 时才写标记**；若用户先买克隆、尚未建立装置，则**静默无副作用、不退钱**。影响面小（克隆前提是已有装置），但属同类缺陷。

## 4. 影响量化

- **现金**：7 个在售商品付费后无交付，合计标价 ¥39 + ¥568 = ¥607 的单次损失风险，且涉及「付款后零反馈」的体验/合规问题。
- **积分**：`cloud-worship`(5850) + 6 个服务(1500~39600) 均挂了 `pointsPrice`、会出现在 `/points` 兑换页 → **兑换即白扣积分且无交付**，性质比现金更严重（用户主动消耗资产却无所得）。
- **根因**：`simulatePay` / `redeemItem` 用 `if (type === ...)` 逐类硬编，新增类型（`cloud_worship`、各 `memorial_service`）从未接上履约；平台有「实体发货」和「虚拟库存」两类载体，却**没有「人工服务受理」这一载体**。

---

## 5. 建议修复（待确认范围）

### 方案甲：补齐「服务受理」载体（推荐，彻底闭环）
1. 新增 `ServiceFulfillment` 模型：`orderId / productId / userId / status(pending→processing→done) / intake(JSON) / adminNote`。
2. `simulatePay` 与 `redeemItem` 对 `cloud_worship` 及非讣告 `memorial_service` 创建受理单（`pending`）。
3. 商品页对这类服务加「购买后请填写需求」入口；控制台新增「我的服务」展示受理状态。
4. 后台新增「服务工单」列表，支持受理/完成。
5. 复用同载体，7 个商品一次闭环。

### 方案乙：最小止血（先避免「白扣」）
- 在 `redeemItem` 中对 `cloud_worship` 及非讣告 `memorial_service` 返回「该服务暂不支持积分兑换」并拒扣；
- 商城/积分页对这 7 个商品**隐藏或标注「敬请期待」**，暂不开放购买，直到方案甲落地。

> 注：最初的「电子讣告发布」也是这套缺陷，当时只补了 `e-obituary` 一个分支；本次审计发现的 7 个，是同一根因的其余暴露面。

### 闭环机制

- 支付/兑换成功 → 自动建 `pending` 受理单（`orderId` 或 `redemptionId` 溯源）。
- 用户在控制台「我的服务」提交需求（intake/contact）→ 管理员后台「服务工单」受理（processing）→ 完成（done）/ 驳回（rejected），状态同步回控制台徽标。
- 积分路径发放失败**真退积分**，不留「扣了分却没拿到受理单」的静默债。
