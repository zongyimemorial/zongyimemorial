# 纪念馆 / 宗祠 存储空间容量体系（免费额度 + 按年升级）

> 单一事实来源：`lib/storage.ts` 的 `STORAGE_PLANS` 与三个常量。
> 商城商品 seed：`prisma/seed-storage.mjs`（**手抄一份**，两处需同步，脚本内有一致性校验）。

## 0. 产品口径（已与业务确认）

1. **计费模式**：按年订阅（365 天租期），与空间装修租期（`lib/hall-decor.ts` 的
   `nextExpiry`）同构 —— 未过期顺延、已过期从今天起算。**到期回退到免费额度，
   已上传的资料不删除，仅限制新上传**。
2. **免费额度**：纪念馆 **1 GB**、宗祠 **2 GB**（建馆/建祠即赠，永久有效）。
3. **与高级订阅彻底解耦**：容量只由「免费额度 + 已购容量包」决定，**单一判据**；
   `premium` 仅保留「单张 20MB 高清原片上传」权限，**不再决定容量上限**。

> 为什么强调"单一判据"：本仓库反复踩「同一个事实有两个判据」的坑
> （premium 三种语义分叉曾导致「宗祠装修后无法保存」）。容量判定的唯一出口是
> `effectiveStorageQuota(hall, kind)`，上传接口 / 控制台 / 回退全部调它，绝不手写。

## 1. 市场成本基准

云存储裸成本（2025–2026 中国大陆，标准存储，元/GB/月）：

| 厂商 | 挂牌价 |
|---|---|
| 阿里云 OSS | 0.09–0.12 |
| 腾讯云 COS | 0.099 |
| 华为云 OBS | 0.099 |
| AWS S3 北京 | ≈0.17 |

取公开挂牌中位 **0.10 元/GB/月 = 1.20 元/GB/年**。
另有请求费（GET 0.01 元/万次）、下行流量（0.15–0.5 元/GB），**平台自担、不向用户收流量费**。

**平台有效成本假设（透明披露）**：照片经 WebP/AVIF 压缩约 1/3、旧视频转冷归档
（0.03 元/GB/月）、用户平均利用率 <80% → **有效成本 ≈ 标称的 1/3 ≈ 0.40 元/GB/年**。
下方毛利率按「标称裸成本 1.20/GB/年」保守计算（实际更高）。

## 2. 档位与利润测算

| 档 | 容量/年 | 价格/年 | 标称裸成本 | 毛利率(按裸成本) | 适用 |
|---|---|---|---|---|---|
| 免费 | 1GB(馆)/2GB(祠) | ¥0 | — | — | 基础纪念空间 |
| 标准 | 10 GB | ¥29 | ¥12 | **59%** | 单人完整生平+影像 |
| 进阶 | 50 GB | ¥99 | ¥60 | **39%** | 丰富照片墙+多段视频 |
| 专业 | 200 GB | ¥299 | ¥240 | **20%** | 家族合集/长视频 |
| 旗舰 | 500 GB | ¥599 | ¥600 | ≈0%(裸) / 高(有效) | 大宗家族档案 |

- **最高档封顶 500GB**：纪念场景真实需求 ≤200GB，封顶避免「卖 1TB 必亏」的裸成本倒挂。
- **积分价**：与平台既有 1:1 口径（100 积分 = ¥1），`pointsPrice = priceFen`，开放积分兑换。
- **利润结论**：低/中档毛利 39–59%（健康）；高档在标称裸成本下偏薄，
  但在「压缩+冷存+低利用率」有效成本假设下仍显著盈利。**定价保证平台正向利润**。

## 3. 数据模型（`prisma/schema.prisma`）

`MemorialHall` / `ClanHall` 各加三列（容量**每馆/祠独立**）：

```prisma
storageSubBytes  Int        @default(0)  // 已购容量包字节（订阅 add-on）；0 = 仅免费额度
storageUsedBytes Int        @default(0)  // 当前已用字节（上传 + / 删除 -）
storageUntil     DateTime?               // 容量订阅到期；null = 仅免费额度
```

`ProductType` 枚举加 `storage`；`Order` 加 `targetHallId` / `targetKind`（容量包作用对象）。

迁移：`prisma/migrations/20261001000100_add_storage_quota`。

**回填**：`prisma/backfill-storage-used.mjs` —— 按磁盘 `fs.stat` 累加各馆 `archive.photos`
（只统计本系统托管图片，外链不占容量），**覆盖写**故可反复跑。
不先回填的话，老馆"已用"从 0 起算，一上传就可能被判"满"。

## 4. 单一判据（`lib/storage.ts`）

```ts
effectiveStorageQuota(hall, kind) = 免费额度(kind) + (订阅有效 ? storageSubBytes : 0)
```

- `isStorageActive(hall)`：`storageUntil` 是否在有效期内。
- `storageSubBytesOf(hall)`：过期即回退 0。
- 顺延复用 `hall-decor.ts` 的 `nextExpiry(existing, 365)`。

## 5. 履约（`lib/pay.ts` simulatePay）

- 新增 `storage` 分支：按 `order.targetHallId` / `targetKind` 回写对应馆的
  `storageSubBytes` + `storageUntil`（**必须传 tx**，与 decor 分支同构）。
- 旧 `premium-storage` 订阅商品（**2026-10 已下架**）：履约分支**保留**（存量已购订单
  不能因为下架就失效），仍然直接写容量包（历史档位 = 进阶 50GB），不写 `premiumStorage` 标记。
  下架原因见 §6.5。

## 6. 上传接口（字节级配额）

`app/api/halls/[id]/upload/route.ts` 与 `app/api/clan-halls/[id]/upload/route.ts`：

- 去掉旧的张数上限（`cap = isPremium ? 500 : 20`）。
- 改为 `used + file.size > effectiveStorageQuota(hall, kind)` 则拒绝；
  成功后 `storageUsedBytes: { increment: file.size }`。
- **单张大小上限**：`maxImageBytes(hall)` → 20MB / 8MB。判据是 `hasHdUpload()`，
  见 §6.5。
- 删除照片（`removeHallPhoto` / `removeClanHallPhoto`）：`statManagedUpload(url)` 取大小后
  `storageUsedBytes: { decrement }`，防容量只增不减。

## 6.5 单张 20MB 高清原片：并入容量包（2026-10）

### 起因：商城并列两个同价同容量的存储商品

| | `premium-storage`（已下架） | `storage-50g` |
|---|---|---|
| 价格 | ¥99/年 | ¥99/年 |
| 容量 | 50GB | 50GB |
| 积分兑换 | ❌ 不支持 | ✅ 9900 积分 |
| 单张图片上限 | 8MB → **20MB** | 无（走全局判据） |

**用户直接的疑问就是「这两个产品是不是重叠了」** —— 是重叠，而且是三重危害：

1. **同价同容量并列** → 用户无法二选一，只能凭运气点；
2. **价格歧视** → 一个能积分兑、一个不能；
3. **第二判据** → `premium-storage` 的容量由 `premiumUntil` 隐式推导，
   绕开了 `lib/storage.ts` 的 `storageSubBytes`。这是本仓库已踩过多次的
   「同一个事实两个判据」老毛病（参见 `AGENTS.md`）。

根因：`premium-storage` 属于"premium 时代"的商品，它的容量口径写在 `pay.ts` 里
（`BigInt(50 * GB)`），**不来自 `STORAGE_PLANS`**。

### 处置

1. **下架** `premium-storage`（`status = inactive`），商城不再展示；
   履约分支保留，存量已购订单照常生效。
2. **单张 20MB 权限并入容量包**（全档位），判据抽成 `lib/storage.ts` 的 `hasHdUpload()`：

```ts
hasHdUpload(hall) = isStorageActive(hall) || premiumUntil 有效
```

保留 `premiumUntil` 一支，是为了**不剥夺存量已购用户的权益**（库里有 2 个馆带有效
`premiumUntil`）。

> 顺带修掉一个荒诞反差：用户花 **¥599 买 500GB**，想传一张 12MB 的高清原片被拒，
> 提示还写着"升级高级订阅"——而那个"高级订阅"只有 **50GB**、比容量包还少。

### 深链改向（6 处）

| 位置 | 原指向 | 改为 | 理由 |
|---|---|---|---|
| `console/halls/[id]` ×2 | `/mall/premium-storage` | `/mall/storage-50g` | 语义=扩容，落到容量包 |
| `console/clan-halls/[id]` ×2 | 同上 | 同上 | 同上 |
| `components/console/DecorStudio.tsx` | 同上 | `/suites` | 语义=解锁 premium 档**素材**，原指向容量商品本身就是错配 |
| `components/whisper/AvatarPicker.tsx` | 同上 | `/mall/whisper-premium` | 语义=解锁 premium 档**形象**，正主是悄悄话长夜版 |

### 文案

- 拒因从"升级高级订阅可上传 20MB 高清原片"→"**购买存储容量包**可上传 20MB 高清原片"。
- `StoragePanel` 明写权益："开通任一大包即解锁**单张 20MB 高清原片**上传（原 8MB）"。
- `HallPhotoManager` 的 `isPremium` prop **改名 `hdUpload`** —— 沿用旧名会让调用方
  以为传 `premiumActive` 就够，漏掉容量包这条来源。

## 7. 控制台 UI

`StoragePanel`（`components/console/StoragePanel.tsx`，纪念馆 / 宗祠共用）：
进度条（已用/总额、红色接近满）、到期状态（生效中 / 已到期续费 / 免费额度）、
四档升级按钮。升级按钮调 `createStorageOrder` / `createClanStorageOrder`
（Server Action，**带 targetHallId 一步建单**并跳转账页）。

> 为什么不在商城商品页直接买：容量包是**馆级**的，必须带 `targetHallId` 下单；
> 商城商品页是公共页面（可能未登录、也可能多个馆），无法确定目标馆。
> `createOrder` 内做**归属校验**，防"拿别人的馆 id 下单把容量充进他人的馆"。

**反向验证（已做，改完必还原）**：

| 缺陷 | 应变红 | 实测 |
|---|---|---|
| A 改回张数判定 | §1 | ✅ |
| B `effectiveStorageQuota` 读 premium | §0+§1 | ✅ |
| C 履约不写 `storageSubBytes` | §1 | ✅ |
| **D** `hasHdUpload` 去掉容量包分支 | §0 三条 | ✅ 4 条精确变红 |

> ⚠️ **缺陷 E 第一次没让「重叠加」变红** —— 因为该断言只从商品名抽容量，
> 而 `premium-storage` 名字里没写容量，被算成 `9900/-1`，与 `storage-50g` 的
> `9900/50` 不同组 → **断言恒绿（假绿）**。
> 修法：容量来源取两处 —— 名字里的 + `pay.ts` 里刻的历史档位映射。
> **这条教训值得记：断言自己也会假绿，反向验证是唯一能发现它的手段。**
