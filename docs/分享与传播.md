# 分享与传播

> 2026-10 定案。验收 `scripts/verify-share.mjs`（67 项，含四组反向验证）。

## 一、要解决的问题

> 平台中的文章及纪念馆、宗祠均可以分享至微信、头条等社交平台。
> 无论是深藏于云端的历史文献，还是承载血脉精神的影像记录，
> 都能通过一键分享触达更广泛的受众。

一句话目标：**让"分享出去"这件事，从"复制链接再切 App 粘贴"
降到"点一下"。**

## 二、国内社交平台的现实约束（决定设计）

**微信、头条没有官方 Web 分享接口。** 这不是实现偷懒，是平台生态的事实。
所有"分享到微信"的 Web 方案，本质只有三种：

| 方案 | 可行性 |
|---|---|
| `navigator.share()` | ✅ 手机端唤起**系统分享面板**，微信/头条都在面板里 |
| 二维码扫码 | ✅ 桌面端唯一能进微信的路 |
| Web 直链（微博/QQ空间/豆瓣） | ✅ 这些平台有公开接口 |
| ~~微信 JS-SDK~~ | ❌ 需要公众号 + 域名备案 + 签名服务，重且脆 |

所以分渠道：

```
手机端 → navigator.share()（系统面板，含微信/头条）
桌面端 → 二维码（手机扫码即开）+ 微博/QQ空间/豆瓣直链
兜底   → 复制链接
```

## 三、组件结构

```
components/share/
├── ShareBar.tsx        # 横条：主分享按钮 + 二维码 + 复制 + 平台直链
```

**挂载点**（三处）：

| 页面 | 路径 | scope |
|---|---|---|
| 文章详情 | `/news/[slug]` | `news` |
| 纪念馆公页 | `/halls/[id]` | `hall` |
| 宗祠公页 | `/clan/halls/[id]` | `clan` |

## 四、二维码：为什么自研 + 怎么保证没写错

**自研理由**：① 内测隧道抖动 + 零外部资源原则，少一个依赖少一处风险；
② SVG 可断言（验收脚本能数矩形），canvas 不能；③ SSR 安全，无水合 mismatch。

**自研 QR 最大的坑是"看起来对但扫不出来"** —— 编码器错了仍会画出一个
像模像样的方阵，肉眼完全看不出。所以**必须用独立实现交叉验证**：

```bash
# /tmp/qrverify：第三方 qrcode 生成参考矩阵 + jsqr 独立解码往返
node scan.mjs   # 5/5 PASS（含中文、完整分享 URL）
```

实测抓出的错（都会导致扫不出）：
1. **分块/交织参数表几乎每行都错** —— 照 `qrcode` 的表逐版本核对；
2. **格式信息 / 版本信息 / 保留区的写入位置错** —— 照 spec 重写；
3. **惩罚分值（掩码选择）规则 1–3 有 bug** —— 虽不影响可扫性，但影响可读性。

**容量上限**：`MAX_VERSION = 10`（v11+ 的表太大，刻意不实现），
字节模式上限 **213 字节**。真实分享 URL ≈120 字节 → v7–8，够用。
超长时 `pickVersion` 返回 `null`，**绝不静默截断**。

## 五、内测口令与分享的冲突：签名令牌

**冲突**：内测期全站被 `/preview-gate` 拦着，但"一键分享"承诺点开即看。

**不采用的方案**：`?share=1` 就放行 —— 那是全站后门，任何人拼参数即可绕过。

**采用的方案**：HMAC 签名把令牌**绑死到具体路径**。

```
令牌 = base64url(exp) + "." + base64url(HMAC-SHA256(AUTH_SECRET, `${scope}|${pathname}|${exp}`))
```

于是：改路径 → 签名失配；改有效期 → 签名失配；无密钥 → 无法伪造。

**中间件三点判据，缺一不可**：
1. 路径在 `shareablePathScope()` 白名单内；
2. 签名对该**逐字相同的 pathname** 有效（含 scope）；
3. 必须是 **GET / HEAD**。

放行时**顺手种 `preview_auth` cookie**（否则访客点第二下又被口令页打断）。
**私有路径（/console /admin /pay）结构上永不放行**，即使拿着有效令牌。
令牌有效期 **60 天**，不携带任何身份信息，不授权任何写操作。

## 六、⚠️ Edge runtime 陷阱（本次最贵的教训）

**middleware 跑在 Edge runtime，那里没有 `node:crypto`。**

顶层 `import { createHmac } from "crypto"` → **每个请求 500**。

最阴的是：**500 会让"无令牌应被拦"类断言看起来通过**
（请求确实没到达目标页）→ 假绿一片。

**修法**：`lib/share.ts` 改用 **Web Crypto（`crypto.subtle`）**，函数变 `async`；
middleware 里必须 `await verifyShareToken(...)`
（不 await 拿到 Promise，恒真 = 白名单内**一律放行**，实测无令牌也返回 200）。

**额外发现**：`import("node:crypto")` **惰性加载也救不了** ——
webpack 只要在被 middleware import 链遍历到的模块里看到它，
构建就直接 `UnhandledSchemeError` 失败，连"引用但从不调用"也触发。
**安全的前提是整个文件里根本没有它。** 据此删掉了零调用方的同步版 API。

## 七、隐私口径

| 场景 | 分享卡内容 |
|---|---|
| 公开馆 / 公开祠 | 馆名 + 逝者名（馆主本就把这些公开挂在页面上） |
| **私密馆** | **只显示馆名**，不带逝者名，保持 noindex |
| 待审（pending）祠 | 仅馆主可见；分享可用（发给亲友），noindex |

分享按钮在私密页**仍可用** —— 馆主发给亲友是正当场景。
