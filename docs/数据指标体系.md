# 运营监控 · 数据收集指标体系

> 面向「宗忆堂」运营监控大盘（`/admin`）的数据收集设计。
> 设计目标对应运营方提出的两大诉求：
>
> 1. **了解网站的实际运营状况**（经营健康度）
> 2. **为今后推广收集并分析数据，从而制定最佳推广方案**（获客与增长）
>
> 二者共用同一套采集层，但看数视角不同：前者关注「钱/内容/活动」的存量与当日波动，
> 后者关注「流量从哪来、转化到哪一步、留存如何、地域与设备分布」的增量与结构。

---

## 一、指标体系总览

指标分两组：**A 组（运营状况）** 与 **B 组（推广分析）**。A 组多取自业务主表（订单/用户/馆祠/供奉），B 组取自新建的轻量分析事件表 `AnalyticsEvent`。

| 组 | 维度 | 核心指标 | 数据来源 | 服务目的 |
|----|------|----------|----------|----------|
| A 运营 | 营收 | 今日/近7日/累计成交额、订单数 | `Order` | 经营健康度 |
| A 运营 | 内容 | 纪念馆（已开通/待审）、宗祠、待审核、供奉次数 | `MemorialHall`/`ClanHall`/`ModerationQueue`/`*Tribute` | 内容供给 |
| A 运营 | 业务活动 | 直播、福币、积分 | `LiveSession`/`FortuneLog`/`PointLog` | 活跃业务 |
| **B 推广** | 流量 | 访问会话、PV、UV、新/老访客、DAU/WAU/MAU | `AnalyticsEvent` | 流量规模与质量 |
| **B 推广** | 渠道 | 各渠道访问/注册/付费用户及转化率、GMV | `AnalyticsEvent` | **渠道 ROI 与质量排序** |
| **B 推广** | 转化 | 访问→注册→建馆/建祠→**付费用户**漏斗（人口径） | `AnalyticsEvent` | 找出流失环节 |
| **B 推广** | 营收 | 付费订单/GMV/客单价/ARPPU/复购倍数/付费渗透率（订单·金额口径） | `Order`+`User` | 变现结构与质量 |
| **B 推广** | 留存 | 按注册日的 D1/D7/D30 回访率 | `AnalyticsEvent`+`User` | 增长可持续性 |
| **B 推广** | 趋势 | 每日新增用户/馆/GMV | `AnalyticsEvent`/`User`/`Order` | 节奏与拐点 |
| **B 推广** | 画像 | 访客地域（省）、设备分布 | `AnalyticsEvent` | 投放定向依据 |

> B 组中的「趋势·新增用户/馆/GMV」与「留存」依赖真实业务主表，演示环境若未生成模拟账号会偏空，属预期。

### 双口径约定（重要）

**转化漏斗与营收分析刻意采用两种口径，互不污染**：

| 口径 | 单位 | 指标 | 来源 |
|------|------|------|------|
| **人口径**（转化） | 去重**用户** | 访问/注册/建馆·建祠/**付费用户** | `AnalyticsEvent`（`first_pay` 按 `userId` 去重） |
| **订单·金额口径**（营收） | **订单 / 金额** | 付费订单数、GMV、客单价、ARPPU、复购倍数、付费渗透率 | `Order` 表直读 |

- 采集层 `first_pay` 是「**每笔 paid 订单一条事件**」（`valueFen`=订单金额），用于渠道 GMV 与营收；
  而**漏斗必须按 `userId` 去重**取「付费用户」，否则会出现 `订单数 41 > 注册数 12` 的倒挂，漏斗不可读。
- 因此漏斗里不出现订单数；订单数、GMV 等金额指标统一收进独立的「**营收分析**」板块。
- 实现：`getFunnelMetrics()` 用 `COUNT(DISTINCT "userId") FILTER (WHERE type='first_pay')`；
  `getRevenueMetrics()` 直读 `Order` 表（GMV 的唯一真实来源）。

## 二、采集架构

采用**自建轻量分析层**（数据落自家 Postgres，不外发第三方），三层采集：

1. **客户端埋点** `components/site/AnalyticsTracker.tsx`
   - 生成随机 `visitorId`（localStorage）、管理 `sessionId`（sessionStorage，30min 无活动则新会话）。
   - 监听路由变化，上报 `visit_start` / `pageview`；携带 `?share=` 时上报 `share_open`。
   - `keepalive` 异步上报至 `/api/collect`，首屏零阻塞。
2. **服务端采集 API** `app/api/collect/route.ts`
   - 无鉴权入口，接收客户端事件（数组，≤50 条），经类型白名单校验。
   - 服务端统一富集：`userId`（当前登录）、`device`（UA 解析）、`region`（离线 GeoIP）、`channel`（归因）。
   - 首次访问写入 `acq_channel` 长期 cookie（180 天），供**后续转化归因**（转化事件按首访渠道计）。
3. **服务端转化注入**（`lib/analytics.ts` 的 `track()`）
   - 在建馆、建祠、注册、首单四处关键动作写入 `create_hall` / `create_clan` / `register` / `first_pay`，
     渠道取自 `acqChannelFromCookie()`，保证「转化归首访渠道」口径稳定。

### 渠道归因口径 `classifyChannel()`

优先级：**分享令牌 → UTM（付费/外链） → Referer（社交/搜索/外链） → 直接**。

| channel | 含义 | 判定 |
|---------|------|------|
| `share` | 分享链接 | URL 含 `?share=` |
| `paid` | 付费推广 | UTM medium/source 命中 ad/cpc/paid/sem/投放 等 |
| `referral` | 外部引荐 | 命中 UTM 但非付费，或 Referer 为未知外站 |
| `social` | 社交媒体 | Referer 命中 微信/QQ/微博/抖音/小红书/知乎 等 |
| `search` | 搜索引擎 | Referer 命中 百度/搜狗/必应/360/谷歌 等 |
| `direct` | 直接访问 | 无来源 |

## 三、数据模型 `AnalyticsEvent`

```prisma
model AnalyticsEvent {
  id        String   @id @default(cuid())
  ts        DateTime @default(now())
  type      String   // pageview|visit_start|register|create_hall|create_clan|first_pay|share_open|share_click
  channel   String   @default("direct")
  source    String?
  region    String?  // 粗略省份（中文）或「海外」；私有 IP 为 null
  device    String   @default("unknown") // mobile|desktop|tablet|unknown
  path      String?
  visitorId String?  // 随机匿名
  sessionId String?
  userId    String?
  valueFen  Int?     // 首购金额（分）
  @@index([ts]) @@index([type, ts]) @@index([channel, ts]) @@index([userId, ts]) @@index([region, ts])
}
```

## 四、大盘板块（`/admin`）

沿用既有 `AutoRefresh`（每 60s `router.refresh()` 直读 DB），共 9 板块：

1. **核心指标**（保留）：今日/近7日/累计成交额、今日新增用户。
2. **流量与获客**（新）：访问会话、PV、UV、新/老访客，DAU/WAU/MAU。
3. **渠道来源**（新，推广核心）：各渠道访问/注册/注册率/付费用户/付费GMV/付费率/客单价，附访问占比条。
4. **转化漏斗**（新）：访问→注册→建馆/建祠→**付费用户**（人口径、按 `userId` 去重），含逐级步转化率与整体转化率。
5. **营收分析**（新，与漏斗分层）：累计 GMV、付费订单数、付费用户数（去重）、客单价 AOV、人均付费 ARPPU、人均订单（复购倍数）、付费渗透率。直读 `Order`，与漏斗「人」口径隔离。
6. **用户留存**（新）：按注册日分群，D1/D7/D30 回访率。
7. **运营趋势**（新）：近 30 日每日新增用户 / 新增馆祠 / GMV（纯 CSS 迷你柱状，无外部图表库）。
8. **地域 & 设备**（新）：访客省级 UV 分布、设备占比。
9. **内容与祭献 / 业务活动 / 快捷入口**（保留）。

## 五、合成数据回填与清空

`scripts/backfill-analytics.mjs`（仅写 `AnalyticsEvent`，不碰真实经营主表，可随时清空）：

```bash
node scripts/backfill-analytics.mjs          # 追加 30 天合成访问/转化事件（不删已有）
node scripts/backfill-analytics.mjs --reset  # 清空后重新写入（可重复、幂等）
node scripts/backfill-analytics.mjs --clear  # 仅清空分析层数据
```

回填数据特点：6 渠道按权重分布、22 省+海外地理分布、移动/桌面/平板设备分布、新访客按渠道转化倾向发生注册→建馆→首购、并预置「老访客」种子以保证新/老访客口径成立。**留存与趋势的新增用户/馆/GMV 来自真实主表，本脚本不生成模拟账号。**

### 真实数据重建（当前生产口径）

`scripts/seed-analytics-real.mjs`（**可重复运行**）：先清空旧演示数据，再按当前数据库的**真实业务 1:1 重建**分析事件：

```bash
node scripts/seed-analytics-real.mjs
```

| 事件 | 数量来源 | 说明 |
|------|----------|------|
| `register` | 真实 `User` 数 | 每用户 1 条 + 其真实浏览会话 |
| `create_hall` | 真实 `MemorialHall` 数 | — |
| `create_clan` | 真实 `ClanHall` 数 | — |
| `first_pay` | 真实 `paid` 订单数 | 每笔 1 条，`valueFen`=订单金额（GMV 与 `Order` 表一致） |
| 流量（PV/UV/渠道/地域/设备） | 真实用户量级 + 匿名访客 | 与真实规模一致 |

> `first_pay` 是**订单级**事件（1 条=1 笔订单），用于渠道 GMV 与营收口径；
> 漏斗取「付费用户」时按 `userId` 去重，二者口径分离（见「双口径约定」）。

## 六、合规边界

- 仅存储：随机 `visitorId`、粗略到**省份**的 `region`、渠道 `channel`、设备。
- **不存储**姓名、手机号、邮箱、精确 IP、精确地理位置。
- GeoIP 为**离线**库（`geoip-lite`），无任何运行时外发请求。
- 分析数据仅 `admin`/`editor` 角色可见，对外公开页面不暴露。

## 七、如何用这些数据制定推广方案

1. **渠道质量排序**：在「渠道来源」看 `注册率` 与 `首购率`。分享链接（share）通常质量最高——验证裂变的价值，应优先做「分享得权益」机制。
2. **预算分配**：付费推广（paid）若注册率/首购率低于自然搜索（search）或社交（social），说明投放素材或定向有待优化；把预算从低效渠道挪到高效渠道。
3. **漏斗优化**：若「注册→建馆」骤降，说明建馆流程门槛过高（材料/审核），应简化引导；若「建馆→付费」低，说明付费钩子弱，可强化首单优惠。结合「营收分析」看 ARPPU 与复购倍数——若付费人数少但人均订单高，属「少而深」，应扩付费广度（降低首单门槛）；反之则相反。
4. **留存抓手**：D1/D7 低 → 注册后缺乏激活（欢迎流程、首建馆引导缺失）；D30 低 → 缺乏持续回访理由（忌日提醒、节日活动）。
5. **地域定向**：地域分布偏集中时，可在薄弱省份做本地化内容/线下合作；设备若移动端占比过高，移动端体验与转化需优先保障。
6. **节奏**：趋势图定位 GMV/新增拐点，与推广活动日历对齐，复盘活动 ROI。
