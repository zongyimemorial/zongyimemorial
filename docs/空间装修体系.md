# 空间装修体系

> 适用范围：纪念馆（`/halls/[id]`）与宗祠（`/clan/halls/[id]`）的模板、装饰套件、
> 素材档位、建馆赠品与发货链路。
> 代码入口：`lib/hall-decor.ts`、`lib/clan-decor.ts`、`lib/decor-3d.ts`、
> `lib/decor-products.ts`、`lib/decor-grant.ts`、`components/decor/*`。

## 2. 档位模型

```ts
type DecorTier = "free" | "points" | "buyout" | "premium";
```

| 档位 | 徽章文案 | 获取方式 |
| --- | --- | --- |
| `free` | 建馆赠品 | 只用于赠品模板及其零件，**不标价、不进商城** |
| `points` | `N 积分` / `¥N` | 积分兑换，或商城付费 |
| `buyout` | `¥N` / `N 积分` | 主要走商城付费，**也开放积分兑换** |
| `premium` | 高级订阅 | 只能开订阅，积分买不到 |

> **`points` 与 `buyout` 的区别只是"主推哪种支付"，两种支付方式对用户都可用。**
> 因此工坊里的兑换按钮对两者都亮（早先只对 `points` 亮，`buyout` 点下去会得到
> 「该素材无需兑换」—— 明明锁着却说不用兑换，是最难解释的一类 bug）。

## 3. 四层内容结构（2026-10 扩到四层）

```
礼包（bundle）    → 商品粒度：把 N 个模板/套件/素材打包打折卖，本身不是装修形态
  └─ 模板（template）→ 空间骨架：壁纸 + 地纹 + 挂饰 + 相框 + 字体（五槽全换）+ 空间形态
       ├─ 整店套餐（kit, 含 applies.wall/floor）
       │     → 一键换整套：连墙带地全换，但**保留 templateId**（不动空间骨架）
       └─ 普通套件（kit）→ 只换装饰：挂饰 / 相框 / 字体，**保留用户挑好的墙与地**
            └─ 素材（item）→ 单件：一个槽位的一件东西
```

### 为什么套件要单独存在

用户认真挑过壁纸与地纹之后，通常不愿意被模板一键覆盖。
套件让「我只想换点装饰」这个诉求有地方安放，而不是被迫接受整套替换。

### 整店套餐 vs 普通套件的分界线（2026-10 定案）

| | 改哪些槽位 | `templateId` | 按钮文案 |
| --- | --- | --- | --- |
| 普通套件 | 挂饰 / 相框 / 字体 | **置空**（改回"自定义搭配"） | 应用套件 |
| 整店套餐 | 五槽全换（**含墙与地**） | **保留** | 一键整装 |

**关键决定：整店套餐保留 `templateId`。**
早先的实现是"无论哪种套件都把 `templateId` 置空"，对整店套餐是错的 ——
用户花 ¥59 买「金殿整装包」，结果空间骨架退回 `classic`（2 柱 + 1 枋），
**越买越朴素**。整店套餐换的是"墙面地面陈设"，不是"建筑骨架"，骨架另有模板管。

判别函数是 `isFullStoreKit(kit)`：`applies` 里含 `wall` 或 `floor` 即为整店套餐。
**判 `applies` 而不是判 `priceFen`** —— 价格会调，形态不会。

### 礼包（bundle）：新的**商品粒度**，不是新的装修形态

`DecorEntitlement.kind` 已扩到 `kit | template | item | bundle`。
礼包卖的是**差价**，所以：

- `listPriceFen`（原价）**由 `bundleListPrice()` 现算**，绝不手写 ——
  手写的"原价 ¥380"一旦与包内调价脱节就成了假广告；
- 发货必须**逐件展开成 `tpl:` / `kit:` / `buy:` 键**（`ent.grants`）。
  只写 `bundle:<id>` = "花了 ¥199 什么都没到手"，与套件早期那个坑同源；
- 商城详情页要**列出包内清单 + 单买合计 + 省多少**（礼包卖的是差价，
  不列清单等于卖盲盒）。

⚠️ 礼包 slug 的坑：`shortId()` **必须先剥 `decor-`**。
礼包 id 是 `decor-bundle-imperial`（自带 `decor-` 前缀），与模板 id `tpl-*` 形态不同。
只剥 `bundle-` 会得到 `decor-bundle-decor-bundle-imperial`（三重前缀，实测踩到）。
现在 `shortId()` 依次剥 `decor-` → `clan-` → `tpl-|kit-|bundle-`。

## 4. 3D 的落地方式：程序化 3D（不是 WebGL）

**决策记录写在 `lib/decor-3d.ts` 文件头**，摘要：

1. 我们跑在 localhost.run 免费隧道上，本就要忍受边缘节点 30–50% 抖动；
   再压一个 ~600KB 的 WebGL 运行时，首屏 3–8 秒，手机端大概率崩。
2. 现有装修体系有一条明确原则：**零外部资源**，纯 CSS / 内联样式
   （见 `lib/hall-decor.ts` 文件头）。
3. 既有的壁龛纪念墙（888 行 SVG）与宗祠四段分镜（942 行 SVG）本来就是
   手绘"伪 3D"：透视、内凹、受光面全是算出来的，不靠任何贴图。

因此走 **CSS `perspective` + `rotateY` + `translateZ`**：

- `lib/decor-3d.ts` —— **表现层**：定义空间形态（几何），不进数据库
- `lib/hall-decor.ts` —— **数据层**：定义装修内容（壁纸/挂饰），进数据库
- 两者通过模板的 `space` 字段关联

> 这样拆的好处：以后要换成 WebGL，只需重写 `decor-3d.ts` + 渲染组件，
> **装修数据与解锁权益一行都不用动**。

### 空间形态（`SpaceKind`）

`classic` 常规厅堂 · `niche` 壁龛纪念墙 · `shrine` 祠堂寝堂 · `courtyard` 庭院天井 ·
`gate` 山门 · `hall` 享堂 · `pond` 莲池 · `starfield` 星河

每种形态描述：相机距离、环视范围、透视强度、地面（纵深/镜面/网格）、
天花板（横梁/穹顶/露天）、墙面几何、陈设摆位、环境光（色罩/主光/强度）。

### 渲染组件

| 组件 | 用途 |
| --- | --- |
| `components/decor/Decor3DScene.tsx` | 底层渲染器：摆墙/地/顶/陈设，负责拖拽环视 |
| `components/decor/DecorSpacePreview.tsx` | 业务封装：`decor` → `spaceKind` 的翻译 + 缺省供案 |

**两条硬约束**（勿改）：

1. **业务文字必须是 HTML 节点**，绝不画进 SVG。
   被验收脚本断言的「堂号」「遗像」「供台」都由调用方以 `children` 传入。
2. **遗像一律真实 `<img>` 叠加**，`borderWidth` 设 0（描金边框由外层提供，避免双描边）。

**拖拽手势绑在「外层」容器**：内层已经在做 3D transform，
手势装在内层会让 hit-test 随 3D 变换漂移，拖拽会"跳"。

**`containerW` 初值必须是确定值**（默认 920），不能由 `window.innerWidth` 推算 ——
服务端没有 window，水合首帧会 mismatch。挂载后由 `ResizeObserver` 校正。

### 空间自带家具（base props，2026-10 新增）

`shrine`（祠堂寝堂）不再只是 `classicSpace` 调几个参数 —— 它自带四件"家具"
（`SPACES.shrine.props`）：**牌位墙、香案、长明灯 ×2**。这些是空间骨架的一部分，
与用户选了什么挂饰无关；`propsFromDecor` 在用户真选了挂饰时会整体替换 base。

**牌位墙不能画成一个 emoji**：`🀄` 放大 1.6 倍也只是"墙上贴了张麻将牌"。
`Prop3D` 对 `tablet-wall` 走专用分支 —— 木色外框 + 3×7 的牌位格
（纯 div + CSS grid，零外部素材）。两个实测踩过的坑：

1. **`left: 50%` 定位的是元素左缘**。小 emoji 看不出偏差，
   几百 px 宽的墙会整体偏右半个身位 —— 必须 `marginLeft: -w/2` 拉回。
2. **尺寸计算不要再乘 `p.scale`**。`propTransform` 里已带 `scale()`，
   两处都乘就是双重放大，墙直接冲出画框。
   因此 `tablet-wall` 的 spec `scale` 恒为 1
   （`propsFromDecor` 里用户选牌位墙挂饰那条路径同样改成了 1）。

**遗像与牌位墙不做格子级对齐**（有意为之）：遗像由 children 以 2D 层居中叠加，
墙是 3D 定位的道具，两套坐标系对不齐是常态；观感是"遗像悬挂在牌位墙前方"，
故格子一律均质、不预留"龛位空格"（预留了也必然错位）。

> **陈旧进程陷阱（又踩了一次）**：guard 每 15 秒轮询，发现 3000 端口空了就会
> 自己拉起 `npm run start` —— 它会赢下与"构建后手动重启"的竞速，
> 用**旧构建**服务；随后新构建覆盖 `.next`，旧 HTML 引用的 chunk 名已不存在
> → `ChunkLoadError` → 错误边界整页替换 → 所有"应该渲染"的断言全灭
> （表现为遗像 0 张、场景 0 个，看着像改坏了，其实服务是旧的）。
> 判据：`/tmp/next-start.log` 里的 `EADDRINUSE` 计数 > 0 就是中招了。
> 正确顺序：杀端口 → **立刻**手动起（抢在 guard 15 秒轮询之前）；
> 或杀完直接等 guard 拉起（guard 服务的也是当前构建）。
> 两者都满足"启动发生在构建之后"。

## 5. 建馆赠品（`granted`）：为什么必须与 `unlocked` 分开

```ts
type HallDecor = {
  templateId?: string;
  slots: Record<DecorSlot, string>;
  unlocked?: string[];   // 我买过 / 兑过什么（buy:<id> / tpl:<id> / kit:<id>）
  granted?: string[];    // 建馆时承诺的赠品模板 id，**永久有效**
};
```

**不能合并进 `unlocked`**：`unlocked` 会被用户的「恢复默认」操作与后台档位调整
反复重写；赠品是**承诺过的权益**，一旦被这两者吃掉，用户就会看到
"说好送的一套装修凭空没了"。

> `resetDecor` / `resetClanDecor` 必须把 `granted` 原样带回 —— 这是最可能出事的地方。
> `scripts/verify-decor-3d.mjs` 单锁这条。

### 甲方案：赠品模板的零件随之永久免费

如果赠品模板用到的零件仍是付费档，用户建完馆看到的是一面**白墙** ——
「赠送一套模板」直接沦为半成品。

`GRANTED_TEMPLATE_PARTS`（`lib/hall-decor.ts`）显式列出每套赠品模板用到的零件：

```ts
"tpl-niche":           ["wall-warm", "floor-marble", "orn-niche-wall", "frame-gold", "font-serif"],
"clan-tpl-ancestral":  ["clan-wall-brick", "clan-floor-stone", "clan-orn-censer",
                        "clan-frame-wood", "clan-font-kai"],
```

**显式列出而不是从 `TEMPLATES` 推导**，是为了让"改了模板 slots 却忘了更新赠品零件"
这件事在代码评审时**一眼可见** —— 推导会悄悄吸收改动，反而更容易出问题。

验收脚本用**集合相等**校验：免费素材集合 ≡ 赠品模板 id + 其零件。
数量口径太松（漏改一件也过）、太脆（加一套赠品就误报），都不用。

> 实测踩到两件：`frame-gold` 是 `premium`（赠品的相框槽用它 → 赠品半残）、
> `clan-wall-white` 漏在 `free`（白送一件本该收费的主力墙面）。集合相等一跑就现形。

## 6. 发货链路

```
商城付费 ──┐
           ├─→ 同一套键：buy:<itemId> / tpl:<tplId> / kit:<kitId>
积分兑换 ──┘
建馆      ──→ decor.granted 追加赠品模板 id（只发新建的那一个馆）
```

| 入口 | 代码 |
| --- | --- |
| 建馆（纪念馆） | `lib/pay.ts` → `issueGrant("hall", id, tx)` |
| 建馆（宗祠） | `app/(public)/clan/halls/actions.ts` → `issueGrant("clan", id)` |
| 货币发货 | `lib/pay.ts` → `resolveDecorEntitlement()` → `issueDecorEntitlement()` |
| 积分兑换 | `app/(public)/points/actions.ts` → 同上 |
| 工坊内兑换 | `app/console/{halls,clan-halls}/[id]/actions.ts` → `unlockDecor()` |

**三条路径必须落到同一个键**，否则会出现"用积分换的锁还在"。

**权益写「用户名下所有对应类型的馆」而不是某一个馆**：素材定价按"件"标的
（¥1–4 一件），用户买的是**使用权**。若限定单馆，用户新建第二个馆时要为同一块壁纸
再付一次钱 —— 在数字商品语境里近乎欺骗。

> ⚠️ 与赠品的区别：赠品只发给**新建的那一个馆**（用户明确要求"只在建新馆时免费赠送一套"），
> 所以赠品走 `granted`、不走 `unlocked`。

### 套件要展开 includes

只写 `kit:<id>` 不够 —— 渲染层是按**素材 id** 判解锁的，
用户会看到"套件已兑换，但里面的挂饰仍然锁着"。
所以套件同时写 `kit:<id>` **和** `includes` 里每件的 `buy:<id>`。

### 积分兑换失败必须真退积分

商品配置有误（如 slug 前缀写错）时，**只把 `PointRedemption.status` 改成 `revoked`
是自欺欺人** —— 积分已经扣了、余额不会回来。必须调 `earnPoints()` 真退回。

## 7. 归一化：为什么模板也要校验

`normalizeDecor()` / `normalizeClanDecor()` 早先只校验「模板 id 存在」——
**收费模板即使没买也会被原样保留，表现为"没买却一直在用"**，权益判定形同虚设。

现在的合法模板来源有四种，判定必须与 action 侧**完全一致**：

1. `tier === "free"`
2. 高级订阅期内
3. 在 `granted` 里（建馆赠品）
4. `unlocked` 含 `tpl:<id>` 或 `<id>`

> 两边口径不一致会出"灵异现象"：action 说能应用、存下去却被归一化掉，
> 页面提示"已应用模板"，刷新后还是旧样子。

**素材侧同理**，且必须带上 `grantedParts`：少了这一条，用户在建馆赠送的壁龛模板里
想把壁纸换回同一块，action 会拒绝「暖木壁纸需 200 积分兑换」—— 而它正在墙上挂着。

## 8. 与供奉体系的边界（用户硬要求）

> 「不管是免费的还是收费的纪念馆与宗祠，供奉祭品均按平台的供奉体系实执。」

机器化表达 = **装修侧模块不得 import 任何供奉模块**。
`scripts/verify-decor-3d.mjs` 扫描 8 个装修模块，确认没有
`from "@/lib/offerings"`。同时校验 `FREE_DAILY_QUOTA === 3` 与
`ALTAR_MAX_ITEMS` 仍在用。

装修**只在表现层**生效：壁纸/地纹/挂饰/相框/字体/空间形态。
**不碰** `OfferingHolding`、`OfferingOnAltar`、`MemorialTribute`、`ClanTribute`
的任何字段或规则。

## 8.5 草稿 / 保存模型（2026-10 新增）

> 用户原话：「装修完了点保存即完成装修」。

### 一句话规则

**逛和试都是草稿，只有「保存并完成装修」落库；但"买"是立即落库的。**

这条分界的理由：如果把「解锁」也做成草稿，用户就能靠"预览后关掉不保存"
白得一套收费素材 —— 预览会变成绕过支付的后门。所以：

| 动作 | 落库时机 | 为什么 |
| --- | --- | --- |
| 点模板 / 换壁纸 / 换挂饰 / 应用套件 | **草稿**（本地 state） | 用户要"放心试搭配" |
| 点「解锁」/ 积分兑换 | **立即写库** | 花钱的事不能只改草稿 |
| 「保存并完成装修」 | **一次性原子写入** | 见下 |
| 「放弃改动」 | 退回上次保存快照 | 不写库 |
| 「恢复默认」 | 立即写库 | 是"清空"，不是"试一下" |

### 为什么是"一次原子写入"，而不是把草稿回放成 N 个 server action

早先的实现是 `applyDecorTemplate` + `setDecorSlot` 两个 action，
前端每点一下发一次。改草稿后如果沿用"保存时逐个回放"，
会有三个问题，前两个是真缺陷：

1. **非原子**：回放到第 3 个 slot 失败 → 库里是"半套装修"，用户看到的是混搭。
2. **N 次往返**：一次保存发 6+ 个请求，免费隧道下 30–50% 会被边缘 503 打掉。
3. **顺序耦合**：`templateId` 必须在下发 slots **之前**写，否则归一化会把
   不属于该模板的 slots 抹掉（`normalizeDecor` 只管已解锁项）。

所以做成 `saveDecor(formData)` / `saveClanDecor(formData)`：
前端把整个草稿 `JSON.stringify({ templateId, slots })` 塞进一个 `draft` 字段，
服务端**校验整份草稿**后一次性写回。

### 关键实现点（`lib/decor-save.ts`）

```ts
export type DecorDraft = { templateId?: string; slots: Record<DecorSlot, string> };
export function parseDecorDraft(raw: string): DecorDraft | null
export function checkHallDraft(draft, ent: DecorEntitlements): SaveCheck
export function checkClanDraft(draft, ent: DecorEntitlements): SaveCheck
```

- **校验的是整份草稿，不只是"改动的那几件"。**
  客户端传来的草稿是**可伪造**的 —— 只校验"这次改了啥"等于把门禁交给前端。
  逐件比对 `isClanUnlocked` / `isUnlocked`，未持有的直接拦下并回 `needUnlock`。
- **写入只覆盖 `templateId` / `slots` / `updatedAt`，`unlocked` 与 `granted` 沿用库里的原值。**
  草稿里不带这两个字段 —— 这是故意的：`granted` 是平台的承诺，
  `unlocked` 是用户花钱买来的，都不能由一次装修保存改写。
- `draftSpaceOf(tpl)` 从草稿的模板推导空间形态，供工坊预览即时切换。

### 客户端的 dirty 判定：快照比较，不是布尔位

`DecorStudio` 用 `contentKey(d) = JSON.stringify({t: templateId, s: slots})`
把当前草稿与 `savedSnapshot` 比对来算 `dirty`。

**为什么不用布尔 `dirty` 位**：那样每个改动点（模板/壁纸/挂饰/相框/字体/套件，
共 6+ 处）都得记得 `setDirty(true)`，以及保存/放弃时 `setDirty(false)` ——
漏一处就是"改了但保存按钮不亮"。快照比较天然免疫这类遗漏：
**状态的真相只有一个来源**。

### 一个反直觉但正确的行为

**草稿条只在 `dirty` 为真时渲染。** 所以"把壁纸换回已保存的那一款"之后，
草稿条会整条消失、「放弃改动」也找不到了 —— 这**不是 bug**，
是"没有未保存改动"的正确表达。

> 踩坑记录：`verify-decor-draft-save.mjs` 早先的"放弃改动"那段依赖前一步的残留状态，
> 于是复跑时（壁纸恰好已是目标值）报「找不到放弃改动」，看着像功能坏了。
> 修法是**不让断言依赖残留状态** —— 自己按需制造一个确定性的 dirty 场景
> （`ensureDirty()` 依次试不同壁纸直到草稿条出现）再断言。
> 判据仍是 AGENTS.md 那条：**同一套件连跑三次都应全绿**。

## 8.7 遗像安奉：两处必须同规格（2026-10）

> 用户反馈：「这两个地方为什么不一样？不统一呢？」（纪念馆 vs 宗祠 截图）

查下来是**三层不统一**。只修一层是不够的 —— 三层各自都会单独造成观感分叉。

### ① 取值口径

| | 早先 | 现在 |
| --- | --- | --- |
| 纪念馆 | `archive.portrait` | 不变 |
| 宗祠 | `archive.portrait ?? hall.coverImage` | **`archive.portrait`** |

宗祠会把**封面建筑照当遗像供进龛里**。封面图的归宿是页面顶部封面位，
不是牌位墙的龛位。统一后两边只认专区上传的那张。

### ② 观感规格

付费 3D 空间（`DecorSpacePreview`）里的遗像早先是**裸 `<img>`**，
纪念馆 128×160、宗祠 120×150 —— 两个数字各自漂移，且**都没有龛体**。

后果很反直觉：**用户花钱升级后，遗像待遇反而变差** ——
从"安奉在墙面正中的大龛"退化成"浮在空气里的一张小照片"。

现在统一走 `components/decor/PortraitNiche.tsx`：

| 规格 | 值 |
| --- | --- |
| 遗像本体 | `PORTRAIT_W × PORTRAIT_H = 150 × 188` |
| 龛体 | 描金外框 + 暗色内衬（模拟龛内进深） |
| 名讳签 | 居中、半透明底、与遗像同宽 |
| 场景高度 | 两边都是 **340**（宗祠原 320） |

尺寸写成**导出常量**，两个页面共用 —— 这正是 AGENTS.md 那条
"遗像 `<img>` 与 SVG 龛位必须共用同一份数字"的延伸：各自漂移就会错位。
`<img>` 自身**不描边**，描金由龛体提供（防双描边）。

### ③ 重复渲染（真 bug）

3D 空间与壁龛墙/牌位墙**曾经可以同时渲染遗像** → 同一页出现两张。

- 纪念馆侧：靠 `isPaidSpace` 排除 `space === "niche"` 而**半遮半掩** ——
  只在"有遗像 + 买了非壁龛模板"时才暴露。
- 宗祠侧：`SceneShrine` **无条件渲染**，只要选了付费模板就必然双份。

现在两边都显式互斥：

```tsx
// 纪念馆
{isNicheWall && !use3DScene && <NicheWallHero ... />}

// 宗祠
<SceneShrine portrait={has3DSpace ? undefined : portrait} ... />
```

`has3DSpace` **必须与渲染分支同口径**（都由 `clanSpaceKind` 派生），
否则会"一处渲染、另一处也渲染"或"两处都不渲染"。

> 宗祠保留牌位墙是**有意**的：牌位墙表达的是"昭穆序"的族谱秩序，
> 与遗像并不重复；摘掉的只有遗像。香案也照常保留 —— 那仍是献祭的落点。

### 验收

`scripts/verify-portrait-unify.mjs`（27 项，连跑三次全绿）。

断言口径是**数遗像 img 的个数**——「恰好 1 张」才是"安奉且不重复"的可证伪表达。
并做了**反向验证**：给一座祠设上真实 `portrait`，确认遗像确实渲染出来，
反证"0 张"不是假绿。

> 反向验证踩了两个坑，都**像功能坏了其实是权限问题**：
> 测试选中的常是 `verify-clan-e2e` 刚建的祠（`status=pending`）——
> ① 匿名访客走"仅你可见"分支，场景不渲染；
> ② **管理员也打不开，拿到 404**（pending 祠只对馆主本人可见）。
> 解法：用 `user@test.com`（馆主）登录，且**只挑 `active` 的祠**；
> 并在断言前先探测"当前身份能打开目标页"。

### ④ 查表函数：宗祠侧必须用 findClanTemplate（真 bug，2026-10）

宗祠公页一度写成 `import { findTemplate } from "@/lib/hall-decor"`
—— 那是**纪念馆的**模板表。于是：

```
findTemplate("clan-tpl-ancestral3d")  →  undefined
clanSpaceKind                          →  undefined
has3DSpace                             →  false
宗祠的付费 3D 空间                      →  【从来不渲染】
```

用户花 1700 积分买了「牌位寝堂 · 立体」，在祠页上**什么都看不到**。
而页面不报错、不警告、照常显示（走回落分支）—— 这就是它最难被发现的地方。
TypeScript 也拦不住：两个函数签名兼容。

这与"商城装修商品详情页要查两边模板表"是**同源问题**：纪念馆与宗祠是**两套**模板表。
商城页正确地写了 `findTemplate(id) ?? findClanTemplate(id)`，宗祠公页却漏了。

断言分两层（`verify-portrait-unify.mjs`）：

| 层 | 条数 | 内容 |
| --- | --- | --- |
| 源码 | 3 | import 来源、调用名、**不得**出现 `findTemplate(decor.templateId)` |
| 运行时 | 3 | 造出"付费模板 + 有遗像"的祠，真去数 `[data-decor-3d]` |

**已做反向验证**：把代码改回 `findTemplate` → **6 条断言同时变红**
（含核心那条「没找到 `[data-decor-3d]`」）。

> 排查时踩的坑：用 psql 复现"有遗像 + 付费模板"时**只写了 `templateId`、
> 忘了写 `unlocked`** → 归一化把未持有的模板 id 静默丢弃 → 页面照旧不渲染 3D。
> 看起来像"改了没用"，其实是**自己没造对前提**。
> （该行为是正确设计：防"没买却一直在用"，见 §7。）

## 8.8 整店套餐的消费端（阶段 5，2026-10）

数据（三个整店套餐：`kit-imperial-hall` ¥59 / `kit-scholar-retreat` ¥22 /
`clan-kit-ancestral-grand` ¥69）在阶段 3 就已就位，但 `applies` 字段
**此前没有任何组件读** —— 写了 `applies` 不等于自动生效。

### `kitSlots()`：applies 优先，前缀推断只给旧套件兜底

```ts
function kitSlots(kit) {
  if (kit.applies && Object.keys(kit.applies).length > 0) return { ...kit.applies };
  // 回退：按 id 前缀扫 includes
  ...
}
```

**顺序不能反。** `applies` 是数据层显式声明的"点一下落到哪五个槽位"；
`includes` 是"买到手的零件"（权益）。两者语义不同（见 §3）。
早先只读 `includes` 靠 id 前缀猜，是**碰巧推对** —— 正确性挂在
"素材 id 命名规范"这个约定上，坏起来静默（某槽位没换、不报错）。

### 三个坑（都踩过）

**① `applies` 与 `includes` 可能不同值。** 这正是"前缀推断"不可靠的证据。
反向验证时若只注释掉 `kitSlots` 的 applies 分支，**测不出来** ——
因为三个套餐的 includes 与 applies 恰好同值。必须同时把 `applies` 改成
`includes` 之外的真实素材，两条路径才分叉。

**② 验收断言的期望值不能由被测逻辑自己产出（"自产自销"假绿）。**
组件把套件声明渲染成 `data-kit-slots` 供脚本断言，最初写成
`JSON.stringify(kitSlots(kit))` —— 而 `kitSlots()` 正是被验收的逻辑。
于是缺陷版下"实际应用"错、"声明"也错，**两边自洽 → 断言绿着通过**。
修法：**直接取数据层 `kit.applies` 原值**，绕开 `kitSlots()`：
`data-kit-slots={JSON.stringify(kit.applies ?? kitSlots(kit))}`。
`kitSlots()` 仍作兜底，但兜底结果**不用于断言**。

**③ 通知用户"套件到底换了什么"。** 两类套件的卡片文案必须分叉：
普通套件写「只换挂饰/相框/字体，保留你挑好的墙与地」，
整店套餐写「含墙与地」+ 按钮「一键整装」。用同一句文案会让用户误判。

## 8.9 档次阶梯：为什么用**价格档**而不是结构档（阶段 5，2026-10）

`DecorTierLadder` 让用户看到"我在哪一档、升一档差多少"。

### 结构档位会给出反直觉结论

直觉上该用 `structure`（`none|basic|grand|imperial`），但实测发现：

- `starfield` 空间的 `structureTier` 是 **`none`**（"星河"是"无建筑构件"形态，
  这是渲染层刻意的定义）；
- 于是「星河长明」（最贵的模板之一）被算成**最朴素档**。

结构档位衡量的是"画了多少建筑构件"，不是"用户花了多少钱、看着多华贵"。
**用户理解的"档次"是后者 —— 所以用价格档。**

四档区间（与 `verify-decor-pricing-v2.mjs` 的口径一致）：
免费 ¥0 / 入门 ¥5–15 / 中档 ¥15–39 / 豪华 ¥39–99。
**区间写死**，不按素材价现算 —— 现算会随素材增减抖动，
用户下次进来看到"豪华档 ¥39–99"变成"¥45–99"，像是偷偷涨价。

### ⚠️ `priceFen` 单位坑：在同一个组件里踩了**两次**

`priceFen` 是**分**，`priceYuan()` 返回**元**。`TIER_BANDS` 的 `min/max`
写成哪一档，决定了对不对 —— 而两次都是"阈值字面量跟着隔壁那处的单位写"：

1. 判「当前档」时手写 `curPrice < 1500 ? "entry" : ...`（元比分）→ ¥99 恒落"入门档"；
2. 修了 ① 之后**统计各档套数那处没改**（`y >= d.min` 同样是元比分）→
   "可选套数"长期显示 `entry:0 mid:0 lux:0`，只有 `y === 0` 的免费档是对的。

现在 `TIER_BANDS` 的 `min/max` 统一用**元**，且 `range` 文案与 `min/max` 严格一致
（改一处必须改另一处，肉眼能对上号）。

### 断言为什么用"合计守恒"而不是"某档 > 0"

`verify-decor-studio-v3.mjs` §4 断言 **各档可选套数之和 = 模板总数**。
比"每档都 > 0"强得多：

- "每档 > 0"测不出区间边界写错（如 mid 写成 `[15,39)` 少了 39 → 落进 lux，
  各档仍都 > 0，但计数错了）；
- **合计守恒**对单位错、边界漏、区间重叠、区间有缝**全都敏感**。

另加一条"至少有一档非 0"，堵掉"合计=总数=0"的假绿
（两边都空时 `0 === 0` 恒真）。

### 当前档断言必须断言"变成了什么"

早先只断 `cur0 !== cur1`（"变了"）—— 那是**弱断言**，正是它让上面的单位 bug
蒙混过关（bug 版下点 ¥99 得到 `entry`，与 `cur0=free` 相比"确实变了"）。
现在断言 `cur1 === "lux"`。**断言"变成了什么"才守得住口径，
断言"变没变"只守得住"接没接上"。**

## 8.10 整页预览：`DecorPagePreview`（阶段 5，2026-10）

工坊里的全屏预览原来只有"3D 空间"一个 tab，用户看不到**馆页整页**会变成什么样。
`DecorFullPreview` 现在有两个 tab：`space` / `page`。

### 复用 `HallDecorLayer`，不内联重写

`DecorPagePreview` 直接复用公页的装修层与 `lib/decor-skin.ts` 的四个 helper
（`skinCardStyle` / `skinTitleStyle` / `skinDividerStyle` / `skinButtonStyle`），
保证"**预览 = 公页**"。在预览里另写一份样式，就会漂移成"预览好看、公页难看"。

### 必须传 `withDark` 回写过的 skin

```ts
const previewDark = skinOf(current, {}).dark || darkDecor;
const previewSkin = withDark(skinOf(current, {...}), previewDark);
```

`darkDecor` 由调用方（两个控制台页）传入 `isHallDarkDecor(decor)` /
`isClanDarkDecor(decor)` 的结果。理由与阶段 4 一致：**让"文字色"与"卡片底色"
来自同一个判据**，否则深色墙上白字压浅米底（见 AGENTS.md 阶段 4 那条）。

### 三个实现细节

- **不含 3D 场景** —— 预览层里再挂一个 3D 会污染
  `[data-decor-3d]` 的计数（对比视图断言 `=== 2`），也不必要。
- **`fixed` 定位要治**：容器加 `transform: translateZ(0)` + `contain: paint`。
  祖先有 `transform` 时，后代的 `fixed` 改为相对它定位 ——
  不加会让预览里的浮层飞到视口外。
- **隐私**：不出现逝者照片，用堂号占位。预览是工坊内的界面，
  但它的 DOM 结构可能被任何截图/分享带出去，所以按公共页面的标准处理。

## 8.11 公页切换 v2（阶段 6，2026-10）

v2 引擎（结构层 + 六层光影 + 材质）在阶段 0–5 里**只在工坊**里跑；
公页一直走 v1，这是刻意的分阶段切换。阶段 6 把**三处公页**一起切到 v2：

| 入口 | 文件 | 空间形态来源 |
| --- | --- | --- |
| 纪念馆馆页 | `app/(public)/halls/[id]/page.tsx` | 服务端算 `spaceKind` |
| 宗祠祠页 | `app/(public)/clan/halls/[id]/page.tsx` | `clanSpaceKind`（`findClanTemplate`） |
| 商城装修商品详情页 | `app/(public)/mall/[slug]/page.tsx` | 由权益 `resolveDecorEntitlement` → 模板 `space` |

### 切法是「显式传参」，不是改默认值

三处各自写 `engine="v2"`，`DecorSpacePreview` 的默认值**仍是 v1**。
默认值是"回退开关"：出问题改调用处一处即可单独回退某页；
改默认值会让"没传"变成"悄悄用上 v2"，回退时得到处找。

原哨兵断言（`verify-decor-scene-engine.mjs` §6"公页暂未启用 v2"）**翻面**为
正面断言：三处都必须显式传，且**点名漏切的那页**。
翻面不是放宽 —— 是把监控点从"别提前切"推进到"必须切齐"。

### 为什么"必须切齐"值钱

用户花积分/钱买的空间，**在工坊里看到的样子必须等于在公页上看到的样子**。
三者不一致时用户会说"我买的立体堂殿，在馆页上怎么变平了"。
所以新套件 `verify-decor-public-v2.mjs` 的断言全是**行为级**（真开页面读 DOM）：
`data-engine="v2"` + `[data-structure-layer]` + `[data-light-layer]`
+ 六类构件分类至少 3 类。

### ⚠️ 「标记不得撒谎」那条断言不能单独用

`(data-engine === "v2") === hasStructureLayer` 守的是"标记与实际同口径"
（阶段 4 踩过 `data-page-skin` 报 `off` 而实际已被深色皮肤接管 —— 同构风险）。
但反向实验证明：**当你去掉 `engine="v2"` 时，v1/v1 两边自洽，它照样 PASS**。
它守不住"有没有切"。必须与「`engine === "v2"`」配对，缺一不可。

反向实验 C（`data-engine` 硬写 `"v2"` 但实际走 v1）证明它有效：
**8 条变红**并点名 `engine=v2 structure=false`；同轮商城页（真 v2）仍 PASS，
说明它**有区分度**。

### ⚠️ 前提必须自己造：库里默认没有任何馆/祠配了付费空间模板

公页 3D 有门禁：
- 馆页 `use3DScene`：要选**付费**模板（赠品 `tpl-niche` 被排除）
- 祠页 `has3DSpace`：`clanSpaceKind` 非空（赠品 `clan-tpl-ancestral` 同理）
- 商城页：`space !== "classic"` 才出预览

而实测**全库 0 行**配了模板。所以"不造前提直接测"会得到 `data-decor-3d` **0 个**，
"没找到结构层"这类断言在空场景下**恒成立** —— 全绿但什么都没测。
新套件 §0 用 psql 造前提（`tpl-goldhall` / `clan-tpl-imperial` + 写 `unlocked`），
`finally` 按**备份逐字还原**。

> 连带发现：既有的 `verify-mobile.mjs` ③/④ 两条 `clipped()` 断言同样依赖这个前提。
> 阶段 6 实跑时先单独验过一次，那时库里 0 个场景 —— `clipped()` 报绿其实是
> "页面没渲染任何 3D"的假绿。造前提后连跑三次仍 29/29，才算真绿。

### 两个断言写法上的教训

- **还原判据要"等于备份"，不要"不等于实验值"**。
  第一版 `back !== "clan-tpl-imperial"` 立刻假红：样本祠原本（手工造的前提残留）
  `templateId` 就是它 → 还原成功但值没变 → 误报"没还原"。
  与 §8.9「变了是弱断言」同源。
- **遗像尺寸断言要有前提**。实测**全库没有任何宗祠有遗像**，
  祠侧那两条会常年 SKIP、永远不被覆盖。修法：§0 借一张纪念馆已有的图片路径
  挂到样本祠上（同机同 uploads 目录），触发渲染，收尾随 `archive` 一起还原。
  现在祠侧能读到真实的 `150×188`。

### `DecorSpacePreview` 的两端模板表兜底链

## 8.12 高级订阅判定：唯一出口（真 bug 修复，2026-10）

### 症状与根因

用户报「宗祠装修后无法保存」——挑好模板 → 点「保存并完成装修」→ **毫无反应**。

根因**不在保存逻辑**，而是**同一个事实有两个判据**：

| | 取源 | 用户级订阅有效、馆级为 null 时 |
|---|---|---|
| 宗祠控制台页 `page.tsx` | 馆级 **OR** 用户级 | UI 显示「高级订阅生效中 · 全部装修素材可用」 |
| `saveClanDecor` 的 `isPremiumOf(hall)` | **只认馆级** | 判「尚未解锁」→ 保存驳回 |

`premiumUntil` 存在于 **User / MemorialHall / ClanHall 三个模型**上，
而 `lib/pay.ts` 买订阅时写的是**用户级** —— 所以只查馆级会漏掉真实用户。

### 为什么 `lib/premium.ts` 没拦住

它文件头写着"唯一实现，新代码一律引用它"，**但一个 import 都没有**（死代码）。
各处 17 处手写判定已分叉成**三种语义**：仅馆级 / 仅用户级 / 并集。

### 口径与修法

**馆级 OR 用户级**（用户买的订阅覆盖他名下所有馆/祠）。

- 新代码用 `isPremiumForUser(user, hall)`（并集）或 `isPremiumUntil(x)`（单来源原语）
- `isPremiumOf` 的参数**从 `hall` 改成 `ctx`**：调用处无法"只传馆"而悄悄退回旧语义
- 收敛后全仓 `grep -rn 'premiumUntil && new Date('` **零命中**

### 验收

`scripts/verify-premium-unify.mjs`（10 项，含反向验证）：

| 层 | 断言 |
|---|---|
| §1 源码 | `premium.ts` 被真正引用（≥6 调用方）+ 宗祠 action 用并集写法 |
| §2 源码 | 全仓无手写 `premiumUntil && new Date(` |
| §3 数据 | **造前提**：馆级 NULL + 用户级在未来 |
| §4 行为 | 真点素材 → 真点保存 → 库里 `updatedAt` **必须变** + dirty 条消失 |
| §5 | 还原到备份值（`premiumUntil` **与 `templateConfig`** 都还原） |

**§3 是核心**：不造那一格前提，整个脚本会全绿而什么都没测。

⚠️ **本套件会改数据，必须连 `templateConfig` 一起还原。**
§4 要验"保存成功"就得真保存一次装修 → 改掉样本祠的 `templateConfig`。
最初只还原 `premiumUntil`，把兄弟套件 `verify-portrait-unify` 跑红
（它对同一座祠断言"实验后 `templateId` 应为空"）。
两处已同时修：本脚本备份+还原 `templateConfig`；
`verify-portrait-unify` 判据改为 **`back === 备份里的 templateId`**（不再写死空串）。

**反向验证**（把 `isPremiumOf` 改回只认馆级）：**精确红 3 条**，
其中 `点保存后库里 updatedAt 真的被改写` 报 `before === after`（正是"没反应"）。
同轮 `控制台页认出高级订阅` **仍 PASS** —— 页面侧一直是对的、只有 action 错，
这就是"分叉"的直接证据。还原后连跑三次均 9/9。

### 10.1 命名与 `space` 必须一致（新增硬约束）

模板名里写了「立体」/「3D」，`space` 就**不能是 `classic`**。

而商品详情页那套预览也跟着哑掉（那边靠 `space` 决定要不要出预览），
