# 供奉体系（消耗式祭品库存 + 供台陈列 + 环境音）

> 本文对应需求：「纪念馆与宗祠下方显示的祭品为前面所购买的祭品（包括免费和非免费的），
> 在祭品点击祭祀后要消失，待下次购买时再显示。另外用户祭拜祭品后纪念馆与宗祠的供台上
> 显示有祭拜的供品，如为音乐，则应该在空间内或宗祠空间内播放该音乐。」
>
> 改造前的行为：祭品面板按 `OrderItem`（买过）来判定可用性，**买一次可以无限次祭拜**；
> 供台只是装饰性的 CSS 图形；音乐祭品只播一段 Web Audio 合成音效。
>
> 改造后：祭品变成**有库存的消耗品**，每次祭拜扣一份；供台记录**每次祭拜**并常驻陈列；
> 音乐祭品在馆内/宗祠空间**循环播放**真实音轨。

## 1. 数据模型

### 1.1 `OfferingHolding` —— 消耗式库存

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `String @id` | |
| `userId` | `String` | 所属用户 |
| `productId` | `String` | 商品（礼器） |
| `quantity` | `Int @default(0)` | **剩余份数**，唯一被扣减的字段 |
| `freeTopUpDate` | `DateTime?` | 最近一次「当日免费补货」的日期；用于幂等 |
| `createdAt` / `updatedAt` | `DateTime` | |

约束：`@@unique([userId, productId])` —— **每个用户每件祭品只有一行**。

设计取舍：之所以用「单行 + 数量」而不是「每次购买一条流水」，
是因为这里要回答的问题只有「现在还剩几份」。流水由既有的 `OrderItem` /
`PointRedemption` / `MemorialTribute` 承担，再加一张流水表只会让"权威来源"变多。

`freeTopUpDate` 用**日期**而不是"已补货"布尔值，是为了支持每日重置：
进馆时若 `freeTopUpDate != 今天`，就把 `quantity` **覆盖**为 `FREE_DAILY_QUOTA`。

> ⚠️ 覆盖而非累加是有意为之。若用累加，用户当天多次进出馆就会无限囤货；
> 用覆盖则并发写也会收敛到同一个值，不需要额外加锁。

### 1.2 `OfferingOnAltar` —— 供台陈列

| 字段 | 类型 | 说明 |
| --- | --- | --- |
| `id` | `String @id` | |
| `hallId` | `String?` | 纪念馆（与 `clanHallId` 二选一） |
| `clanHallId` | `String?` | 宗祠（与 `hallId` 二选一） |
| `userId` | `String` | 谁供的 |
| `productId` | `String` | 供了什么 |
| `clearedAt` | `DateTime?` | **软删除**：非空 = 已撤供 |
| `createdAt` | `DateTime` | 陈列时间 |

**本表刻意不存任何身份字段**（没有姓名、没有联系方式、没有快照）。
供台是"给所有人看的陈列"，一旦落进身份信息，就会成为绕过脱敏设计的泄露通道。
"谁供的"这个问题由 `MemorialTribute` / `ClanTribute` 里那份**已冻结的脱敏快照**回答。

`productId` 的外键是 `onDelete: Restrict`：商品下架不该静默抹掉历史陈列。

## 2. 生命周期

```
        购买（simulatePay / 积分兑换）
                 │  increment
                 ▼
    ┌────────────────────────────┐
    │  OfferingHolding.quantity  │◄── 每日免费补货（覆盖为 3）
    └────────────┬───────────────┘
                 │ 祭拜时 decrement（条件写：where quantity > 0）
                 ▼
          ┌──────────────┐
          │ 库存 -1      │
          └──────┬───────┘
                 │ 同一事务内
                 ▼
    ┌────────────────────────────┐
    │ MemorialTribute /           │   ← 流水（含脱敏身份快照）
    │ ClanTribute                 │
    ├────────────────────────────┤
    │ OfferingOnAltar             │   ← 供台陈列（无身份字段）
    └────────────────────────────┘
                 │ 点「撤供」
                 ▼
          clearedAt = now()（软删除，行保留）
```

### 2.1 免费额度

- 常量 `FREE_DAILY_QUOTA = 3`（`lib/offerings.ts`），**每件**免费祭品每天 3 份。
- 补货时机：**访问纪念馆 / 宗祠页面时惰性补**，不依赖 cron。
  理由：没有定时任务也能正确工作；用户不来的日子不需要补货。
- 幂等：靠 `freeTopUpDate` 判断"今天是否已补过"。

### 2.2 并发安全

扣减用**条件写 + 检查影响行数**，不用"先读后写"：

```ts
const res = await prisma.offeringHolding.updateMany({
  where: { userId, productId, quantity: { gt: 0 } },
  data: { quantity: { decrement: 1 } },
});
if (res.count === 0) {
  // 再查一次，区分"从未持有"和"持有但已用尽"，好给用户不同的提示
}
```

`WHERE quantity > 0` 把判断和扣减合并成一条原子语句，
从根上避免 TOCTOU（先读到 1、两个请求都判定可扣、结果扣成 -1）。
`verify-product-pricing.mjs` 有一条正则断言守着这个写法。

### 2.3 宗祠的特殊顺序：先扣库存，再扣积分

宗祠的收费供奉要同时动两种资源（库存 / 积分），必须定一个失败时能回滚的顺序：

1. `consumeOffering` —— 扣库存
2. `spendPoints` —— 扣积分
3. 若积分不足 → `refundOffering` —— 把库存加回去，返回「积分不足，需 N 积分」

反过来（先扣积分再扣库存）会更糟：库存不足时积分已经真的花掉了，
而积分流水是**只增不改**的账本，反向冲正远不如"干脆别扣"干净。

## 3. 前台交互

### 3.1 三种按钮状态 —— 「只显示我持有的供品」

产品规则：**面板只列我持有的供品**。没买过的东西不在馆/祠里出现，商城才是"逛"的地方。
（旧版有第四态 `locked`，会把 20 个未购收费祭品全渲染成 `¥N` 价格牌，等同于在面板里挂广告位。）

| 状态 | 触发条件 | 表现 |
| --- | --- | --- |
| `ready` | `qty > 0` | 可点，角标 `×N`（1 份为琥珀色，≥2 份为绿色） |
| `empty` | 持有过但 `qty === 0` | **灰显 + `disabled`，不消失**，角标「已用尽」 |
| `hidden` | **从未持有** | 不渲染（连价格牌都没有） |

**如何区分「持有过」与「从未持有」——这是最容易写错的一处：**

- **免费祭器**：只要商品存在就渲染。`topUpFreeOfferings` 在进馆时给所有免费礼器补货，
  所以它们天然"持有中"；用尽 → 次日自动点亮。这也是新用户不会看到空面板的原因。
- **收费祭器**：`owned` = **`OfferingHolding` 里存在这一行**，**不看 `quantity`**。
  - `lib/pay.ts` 购买时 `upsert` 建行 → 「买过」= 有行
  - 用尽后 `quantity` 归 0 但**行仍在** → 灰显
  - 再买一次 → `increment` 回到 `>0` → **自动恢复点亮**
  - 从未买过 = 没有行 = 不渲染

> ⚠️ 曾把 `owned` 写成 `qtyOf(p.id) > 0`（「有库存才算 owned」），
> 后果是**用尽后 drop 回 `locked`、价格牌又冒出来**，与产品规则相反。
> 页面侧一律用 `const heldIds = new Set(holdings.map(h => h.productId))`，
> 再 `owned: heldIds.has(p.id)`。纪念馆与宗祠两页必须是这个口径。

> ⚠️ **宗祠页取收费礼器不能按"最便宜的前 N 件"开窗。**
> 旧实现是 `orderBy pointsPrice asc, take: 4` —— 用户花 800 积分买的数字烟花
> 排不进前 4，于是**库里有货、面板里永远没有入口**，静默丢功能。
> 正确做法：由 `OfferingHolding` 反查（`include: { product }`），买过什么就查什么，件数不限。
> `verify-offering-panel.mjs` 有专门的回归防护断言锁这条。

**补货引导**：面板标题右侧固定挂「去商城补充供品 →」，
宗祠面板底部另有一行同样的引导 —— 面板只列持有的，那"没得用"时就必须有个明确去处。

> **"用尽后按钮灰显而不是消失"是刻意的。**
> 理由一：按钮消失会让网格塌陷、布局跳动，用户会以为功能坏了。
> 理由二：灰按钮配「已用尽」明确传达了"东西还在、补货后就能再用"。
> 用户的原话正是「供品献祭后即被灰色，重新购买后即恢复点亮」。

### 3.2 供台

- 展示**仍在供台上的**（`clearedAt IS NULL`），按时间倒序，最多 `ALTAR_MAX_ITEMS = 12` 件。
- 面板里是一行 emoji（`[data-altar-slug]` 便于验收定位）；
  同时纪念馆的《壁龛纪念墙》场景、宗祠的香案场景里也会画出对应的 glyph，
  并**避开中央的遗像 / 香炉**，不会互相遮挡。
- 「撤供」按钮把当前用户在该馆/该祠的所有陈列置 `clearedAt`，**不删行**，保留审计痕迹。

### 3.3 图标一致性

`lib/ritual.ts` 的 `SLUG_TO_ICON` 是**唯一权威表**：
面板按钮、面板供台、场景供台三处全部由它派生。
改造过程中曾出现过两张互相矛盾的图标表（同一件祭品在按钮上是 🎶、在供台是 🎼），
统一后这类不一致在结构上不可能再发生。

## 4. 环境音乐

- 音乐类祭品（`free-music` 追思音乐、`free-song` 为 TA 点歌）祭拜后，
  在馆内 / 宗祠空间内**循环播放**对应音轨，直到离开页面或撤供。
- 音轨是**本地合成**的免版税音频，位于 `public/assets/ambient/`：

  | 文件 | 气质 | 用途 |
  | --- | --- | --- |
  | `guqin.mp3` | 古琴，清远内敛 | 追思、寄言、礼仪类 |
  | `fanyin.mp3` | 梵音，诵经回向 | 诵经、祈福、供奉类 |
  | `bell.mp3` | 梵钟，一击一悟 | 钟铃、星月、烟花类 |
  | `kongling.mp3` | 空灵琴 | 灯、乐器、飞升之物 |

- 实现要点：
  - **无缝循环**：按 `f = n / 36`（整数周期）合成，保证 36 秒边界处相位连续，
    再用 `afade` 淡入淡出消掉直流跳变。实测接缝处的不连续度 ≤ 最高 99.9 分位样本差的 3%。
  - **自动播放策略**：播放**永远由点击祭品触发**（点击即手势），
    `useEffect` 里绝不自动开播 —— 否则会被浏览器拦截。
  - 播放器是一个 `hidden` 的 `<audio data-ambient-player>`，**挂在 DOM 上而非游离节点**：
    游离节点在 `document.querySelector("audio")` 里找不到，
    会让"页面上到底有没有在放音乐"的排查得出错误的否定结论。
  - 实物供品（花 / 果 / 茶 / 酒）**不配**环境音 —— 供个水果还放 BGM 太违和。

> ⚠️ `next start` 只服务**构建时**已存在于 `public/` 的文件。
> 因此改动音频后必须重新 `npm run build`，否则会 404。

## 5. 上线顺序（重要）

迁移只**新增两张表**，不改任何既有列，因此向后兼容。但读路径的切换有顺序要求：

1. `npx prisma migrate deploy` —— 建表
2. `node scripts/backfill-offering-holdings.mjs` —— 把历史 `OrderItem` 回填成库存
3. 部署新代码 —— 读路径从 `OrderItem` 切到 `OfferingHolding`

若跳过第 2 步，老用户"买过但还没献"的祭品会凭空消失。

> `backfill-offering-holdings.mjs` **只能跑一次**。
> 它用覆盖语义写 `quantity`，重跑会把用户已经消耗掉的库存又补回来。

## 6. 验收覆盖

| 套件 | 覆盖点 |
| --- | --- |
| `scripts/verify-offering-panel.mjs` | **「只显示我持有的」**：未购收费祭品不在 DOM；献祭用尽→灰显仍在；**重新购买→恢复点亮**；免费按日补货幂等；宗祠/纪念馆共享库存且态一致；**贵礼器不被 take:4 截断**（回归防护）；遗像安奉（纪念馆 **3×3 大龛**、宗祠牌位墙正中）；场景优先布局顺序 |
| `scripts/smoke-clan-tribute.mts` | 补货幂等、扣减到 0、`no_stock` / `no_holding` 分支、发放是叠加、回滚 |
| `scripts/verify-clan-tribute-e2e.mjs` | 每日配额、按次扣减、用尽拒绝、按钮灰显、供台陈列、撤供软删除、**音乐真实播放且循环** |
| `scripts/verify-hall-niche.mjs` | 场景供台 glyph、壁龛图仍唯一且定位不变、**遗像占 3×3 大龛（37 块面板 = 45−9+1）**、**馆内音乐真实播放** |
| `scripts/verify-product-pricing.mjs` | 两表存在、唯一索引、`FREE_DAILY_QUOTA=3`、`ALTAR_MAX_ITEMS=12`、条件写正则、`amountFen:0` 与快照字段仍在、供台表无身份列；面板统计为「已持有 N 件」且**不再出现 ¥N 价格牌** |

一键跑全量：`bash scripts/run-all-verify.sh`
（脚本内已按扩展名选 `node` / `npx tsx`，并用能通吃三种汇总行格式的 grep，避免误报"未产出结果"。）
