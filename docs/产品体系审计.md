# 产品体系审计（重复 / 功能相似产品梳理）

> 审计日期：2026-10-07
> 范围：全站商品（虚拟祭品、纪念服务、纪念馆、订阅、装修商品）
> 状态：**仅审计，未删除**。所有"删除/合并"动作等待人工确认后再执行。

## 0. 产品体系分布在哪些文件

平台商品**没有单一清单**，分散在 5 个 seed / 映射文件里，且注释已自承"两处互相覆盖"的隐患：

| 文件 | 角色 | 主要产出 |
|---|---|---|
| `prisma/seed.mjs` | 核心种子 | 建馆/云祭扫/传记/视频/讣告/扫码云碑/长明灯等核心商品；并把 `memorial_hall` 类整体置 `inactive` |
| `prisma/seed-products.mjs` | 虚拟祭品线 | 免费 10 + 基础/进阶/仪式/场景定制 + 节日限定，共约 40 款 |
| `prisma/seed-product-tiers.mjs` | **定价真理源** | `FREE_SLUGS`(10) + `PAID_RITUALS`(20) + `TIER_SPECS`，价格/免费归属以此为准 |
| `prisma/seed-free-offerings.mjs` | 礼器注册 + 高级订阅 | `RITUAL_META`(30) + `premium-*` 订阅（含已下架的 `premium-storage`） |
| `lib/decor-products.ts` + `lib/hall-decor.ts` | 装修商品 | 30+ 套 `TEMPLATES`、多组 `KITS`/`BUNDLES`，以 `decor-*` 商品在商城售卖 |

> 关键事实：`lib/hall-decor.ts` 自带完整的纪念馆模板/套件体系，在商城以 `decor-*` 售卖——这正是与"模板/风格"类老商品（簇 A）功能重叠的根源。

## 2. 功能高度相似 / 重叠簇

### 簇 A · 纪念馆"模板/风格/墓碑样式" ↔ 装修系统 `decor-*`（最该清理）
| slug | 名称 | 类型 | 状态 |
|---|---|---|---|
| `hall-template-elegant` | 专属纪念馆模板·素雅风 | `memorial_hall` | 取决于 seed 顺序，可能漏网为 active |
| `tombstone-style` | 墓碑样式更换 | `memorial_service` | **仍 active** |
| `homepage-style` | 纪念馆首页风格定制 | `memorial_service` | **仍 active** |

- 与 `lib/hall-decor.ts` 的 30+ 套模板、多组套件/礼包（商城 `decor-*` 商品）**功能完全重叠**。
- 前三者走"人工受理"（`isServiceProduct` 判定），`decor-*` 是自动发货权益——**同一诉求两套机制，运营重复**。
- **建议**：确认装修系统已覆盖后，将三者置 `inactive` 或删除。

### 簇 B · 建馆 / 续费类（随"免费建馆"模式整体失效）
| slug | 名称 | 类型 | 状态 |
|---|---|---|---|
| `digital-memorial-hall` | 数字纪念馆（一年） | `memorial_hall` | `inactive`（seed.mjs 批量置） |
| `family-memorial-hall` | 家族纪念馆（三年） | `memorial_hall` | `inactive` |
| `memorial-renew` | 纪念馆续费（一年） | `memorial_hall` | `inactive` |

- 平台已改为"免费建立纪念馆"（实名 + 人工审核），付费建馆/续费商品全部失效。
- **建议**：整体归档 / 删除；属于历史遗留死商品。

### 簇 C · "灯 / 烛"概念分散
- `online-lamp`（在线点灯 ¥3）、`lamp-year`（电子长明灯年卡 ¥9.8）、`free-candle`（免费点烛）、`free-incense`（免费上香）
- 多个相近入口，用户认知碎片。**建议**：保留"单次点灯 / 年卡 / 免费烛"三层即可，无需更多变体。

### 簇 D · "献花 / 花"概念被多商品瓜分
- `virtual-flower`（虚拟献花 ¥6）、`flower-chrysanthemum`/`flower-lily`（虚拟鲜花 ¥2/¥3）、`virtual-wreath`（虚拟挽联 ¥9）、`free-flower`/`free-wreath`（免费）
- 定位与价格带交叉。"献花"诉求被 4–5 个商品拆分，**建议**收敛命名与层级。

### 簇 E · 云祭扫 ↔ 线上追思会
- `cloud-worship`（云祭扫服务，代客献花点灯诵读 ¥39，`cloud_worship`）
- `online-memorial-meeting`（线上追思会直播 ¥128，`memorial_service`）
- 都是"代客/线上仪式"，定位交叠；若云祭扫已含直播环节则重复。**建议**：厘清边界（代客祭扫 vs 亲友线上聚会），避免用户二选一困惑。

### 簇 F · 存储订阅（已下架的死重复，注释自承）
- `premium-storage`（纪念馆大容量存储年订，`inactive`）与容量包 `storage-50g` **同价同容量并列**。
- `seed-free-offerings.mjs` 注释明确："容量已并入『存储空间容量包』"。属故意下架的重复。**建议**：删除该死商品。

### 6.2 数据库落库结果（已核对）
- `free-letter`：¥800 / `isFree=false` / active（收费礼器，与治理前库内状态一致——冲突只在 seed 层，库早已收敛）

### 6.3 为什么"下架"而不是物理删除行
1. **订单历史完整性**：`OrderItem.productId` 外键引用商品行；下架商品的价格/名称是历史订单语义的一部分（`verify-product-pricing` §2c 明确断言"下架 ≠ 可以乱改价"）。
2. **验收断言依赖**：`verify-product-pricing.mjs` 直接按 slug 查询 `digital-memorial-hall` 的价格断言不漂移——物理删除会让查询落空、验收变红。
3. **兼容分支**：`lib/pay.ts` 对 `premium-storage` 有已购用户权益延续分支，slug 必须可解析。
4. **本仓库既有纪律**：下架商品一律 `status=inactive` + 描述注明（见 `seed-free-offerings.mjs` 对 premium-storage 的处理先例）。
八件受影响商品当前**全部零订单**，未来若确认永不上架，可再评估物理清理（需先迁移/归档 OrderItem 语义）。
