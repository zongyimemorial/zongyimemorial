# 认证与登录安全

> 2026-10 定。本文件记录登录相关的安全设计、一次性令牌机制、以及一次真实的安全修复。

---

## 1. 登录方式总览

| 方式 | 入口 | 凭据 | 状态 |
|---|---|---|---|
| 邮箱/手机 + 密码 | `/login` | `identifier` + `password` | ✅ 主力方式 |
| 手机验证码（短信） | `/login` 切 tab | 手机号 + 6 位验证码 → **票据** | ✅ 内测期 mock 发码 |
| 一键登录（内测演示） | `/quick-login?t=<令牌>` | 服务端签发的 HMAC 令牌 | ⚠️ 内测专用，上线前删除 |

三者最终都汇聚到 NextAuth 的 **Credentials provider**（`lib/auth.ts`），
签发同一套 JWT session（`role` / `idVerified` 完全一致）。

## 2. ⚠️ 已修复的安全漏洞：`smsMode` 免密后门

### 漏洞是什么

`authorize` 曾用一个**明文参数** `smsMode="1"` 跳过密码校验（本意是给短信登录复用）：

```ts
const smsMode = (creds?.smsMode as string) === "1";
if (!smsMode) {
  // 才校验密码
}
```

而 `/api/auth/callback/credentials` 是**公开端点**。于是任何人：

```bash
POST /api/auth/callback/credentials
  identifier=admin@test.com
  smsMode=1
```

即可**免密登录任意账号（含管理员）**。实测在修复前确实拿到了
`authjs.session-token` 并能访问 `/console`（HTTP 200）。

### 怎么修的

把明文开关换成**服务端签发的一次性票据**（`lib/quick-login.ts`）：

```
票据 = base64url(phone) . exp . base64url(HMAC-SHA256(AUTH_SECRET, "sms-verified|phone|exp"))
```

- 验证码校验**通过之后**才签发（`createSmsVerifiedTicket`）；
- `authorize` 只认票据（`verifySmsVerifiedTicket`），且必须满足
  **票据绑定的手机号 == 本次 identifier == user.phone**（防"拿 A 的票据登 B"）；
- 2 分钟过期；HMAC 签名，客户端无法伪造。

### 三层防线（都要保留）

1. **类型层**：`credentials` 只声明 `identifier / password / smsTicket`。
   读 `smsMode` 直接 **TS 编译失败**（`Property 'smsMode' does not exist`）——
   后门无法在不修改 credentials 声明的情况下回归。
2. **逻辑层**：`authorize` 中不存在任何"明文开关跳过密码"的分支。
3. **验收层**：`scripts/verify-auth-security.mjs`（18 项，见 §5）。

> 反向验证：注入明文旁路后，「smsMode=1 免密攻击 → 未拿到 session」**精确变红**。

## 3. 一次性令牌机制（`lib/quick-login.ts`）

两类令牌共用同一套签名，靠 **scope 隔离**，不能互相冒用：

| scope | 用途 | subject | 有效期 | 签发者 |
|---|---|---|---|---|
| `quick-login` | 一键登录 | userId | 10 分钟 | `scripts/make-quick-login.mts` |
| `sms-verified` | 短信已验证 | phone | 2 分钟 | `app/login/actions.ts` |

### 令牌格式

```
base64url(subject) . exp(秒) . base64url(HMAC-SHA256(secret, "<scope>|<subject>|<exp>"))
```

- subject **明文可见但被签名覆盖** → 篡改即失配（校验时必须知道"给谁的"才能重算签名）；
- 改 exp → 签名失配（不能自行续期）；
- 无密钥 → 无法伪造（`AUTH_SECRET` 仅服务端持有）；
- 常量时间比较，避免时序侧信道。

### 关键约束：**不得引入 `node:crypto`**

与 `lib/share.ts` 同源约束 —— 只要 `node:crypto` 出现在被 middleware import 链
遍历到的模块里（**包括惰性 import**），webpack 打包 Edge bundle 会直接失败。
因此本模块**零 import**，只用 Web Crypto（`globalThis.crypto.subtle`）。

## 4. 一键登录（`/quick-login`，内测演示用）

用途：给测试账号签发"手机点开即登录"的链接，免手输账号密码。

### 使用

```bash
# 管理员，1 小时有效
set -a && . ./.env && set +a
BASE_URL=https://zongyimemorial.com npx tsx scripts/make-quick-login.mts admin 3600

# 普通用户，默认 10 分钟
BASE_URL=https://zongyimemorial.com npx tsx scripts/make-quick-login.mts user
```

输出形如 `https://zongyimemorial.com/quick-login?t=<token>`，发到手机点开即入控制台。

### 实现要点（踩过的坑）

1. **必须在 Server Action 里调 `signIn`**（`app/quick-login/actions.ts`）——
   在 Server Component 渲染期调用写不了 session cookie，实测页面会停在"加载中"。
2. **action 里顺手种 `preview_auth` cookie** ——
   否则手机端（本来就没这个 cookie）登录后跳 `/console` 会被中间件弹回口令页。
3. **`/quick-login` 必须加入 middleware 白名单** —— 否则先被口令页拦在门外。
4. **登录走标准密码校验**（密码从 `DEMO_ACCOUNT_PASSWORD` 环境变量读，不写进链接），
   **绝不**借道 `smsMode` 那类免密开关。

### 上线前清理清单

- 删除 `app/quick-login/` 整个目录
- 删除 `lib/quick-login.ts`
- 删除 `scripts/make-quick-login.mts`
- 移除 `middleware.ts` 的 `ALLOWED_PREFIXES` 里的 `"/quick-login"`
- 移除 `.env` 的 `DEMO_ACCOUNT_PASSWORD`

## 5. 验收（`scripts/verify-auth-security.mjs`，18 项）

| 分层 | 内容 |
|---|---|
| §1 源码层 | authorize 无明文开关；票据是唯一免密依据；scope 隔离 |
| §2 攻击面 | 真服务 POST `smsMode=1` → 必须拿不到 session |
| §3 伪造票据 | 真服务带假/畸形 `smsTicket` → 必须拿不到 session |
| §4 不误伤 | 正常密码登录应成功 |
| §5 票据单元 | 正规通过 / 篡改拒 / 伪造拒 / 空拒 / 过期拒 / scope 隔离 |

---

## 6. 通用原则

> **任何"免密 / 跳过校验"的开关，都不能是客户端可传的明文参数。**
> 必须是：**服务端签发 + 绑定主体 + 短时效 + 可验证（签名）的票据。**

反面教材就是 `smsMode`：它把"是否已通过验证"这件事做成了一个客户端可填的字符串，
等于把门锁的钥匙孔开在了门外面。
