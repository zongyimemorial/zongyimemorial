# 建馆审核流程改造说明（多渠道替代核验 + 三通道分层 + 合规底线）

> 适用范围：纪念馆（`MemorialHall`）与宗祠（`ClanHall`）的建立审核。
> 改造目标：把"死守火化证明一种材料"改为**多渠道替代核验 + 三通道分层审核 + 合规底线**。

## 一、背景与问题

原审核流"死守火化证明"存在三处硬伤：

1. **年代久远逝者无法建馆**：祖辈无火化证明（土葬、迁葬、战乱散失）即被挡在门外。
2. **宗祠"pending 却公开"的合规口子**：`ClanHall.isPublic` 默认 `true`，建馆即公开，绕过"先审后显"。
3. **无举报/复核闭环**：公页发现"活人被祭拜""虚假馆"时，用户没有入口，平台也无人工队列。

## 二、材料三梯队（替代核验）

| 梯队 | 类型 | 适用通道 | 说明 |
| --- | --- | --- | --- |
| 第一梯队（法定证明类） | 火化证明 / 死亡医学证明 / 户籍注销证明 / 法院宣告死亡判决 | 标准通道 | 任一即可 |
| 第二梯队（殡葬机构辅助证明） | 骨灰存放证明 / 墓址安葬证明 / 殡仪馆火化情况说明书 | 替代通道 | 无第一梯队时凭此核验 |
| 第三梯队（申述辅助材料） | 历史讣告 / 老照片 / 墓址照片 / 家族记载 | 特殊申述通道 | 配合承诺书 |

宗祠仅补**基础材料**（宗族关系证明 / 族谱记载 / 祠堂历史照片或证明），走标准通道，不做替代/申述分层。

## 三、三通道分层审核

| 通道 | 材料要求 | 审核方式 | 时限 | 公开策略 |
| --- | --- | --- | --- | --- |
| 标准 `standard` | 第一梯队任一 | 系统自动初核 + 人工抽查 | 1–3 工作日 | 通过即公开 |
| 替代 `alternative` | 第二梯队任一 | 纯人工 | ~3 工作日 | 通过即公开 |
| 特殊申述 `appeal` | 第三梯队任一 + 亲属关系证明 + 真实性承诺书 | 高级复核 | 5–7 工作日 | **先仅创建者可见**，60 天内补传正式材料后转公开 |

### 合规底线（不可动摇）

- **实名认证硬性**：建馆前必须 `user.idVerified`（以 DB 为准，非 session）。
- **仅创建者可见**：appeal 通道审核通过后，`isPublic` 保持 `false`，只创建者本人可见，直至补传。
- **补传期限（60 天）**：appeal 在建馆时写入 `supplementDeadline = createdAt + 60d`；期限靠 `effectivePublic` **实时计算（无 cron）**，到期未补传自动维持仅创建者可见，owner 端横幅提示倒计时。
- **投诉举报入口**：公页「举报」按钮建 `HallReport`，进后台「被举报」队列人工处理（handled / dismissed）。
- **真实性承诺书**：appeal 必传，模板见 `public/docs/commitment-letter.md`。

## 四、数据模型

### `MemorialHall` / `ClanHall` 新增三列

```prisma
reviewChannel       String   @default("standard") // standard | alternative | appeal（宗祠侧同样三通道，见 lib/hall-review.ts 的 CLAN_CHANNEL_META）
supplementDeadline  DateTime?                      // appeal 建馆后 60 天补传截止
supplementedAt      DateTime?                      // owner 声明材料补齐时刻（appeal → 转公开）
```

`proofs Json?` 升级为新结构（旧 `{fireProof,...}` 由 `lib/hall-review.ts` 的 `normalizeProofs` 向后兼容）：

```ts
{
  applicantRealName?: string
  applicantIdCard: string
  applicantPhone: string
  relation: string
  relationProof?: string
  materials: Array<{ type: string; label: string; value?: string; url?: string }>
  promiseLetter?: string   // 真实性承诺书 URL（appeal 必填）
  promiseSigned?: boolean
}
```

### 新增模型 `HallReport`（多态举报）

```prisma
model HallReport {
  id String; reporterId?; reporter User? @relation("ReportReporter", ...)
  hallId?; hall MemorialHall? @relation(..., onDelete: Cascade)
  clanHallId?; clanHall ClanHall? @relation(..., onDelete: Cascade)
  kind String @default("living")  // living | fake | other
  reason String?; contact String?
  status String @default("pending") // pending | handled | dismissed
  handlerId?; handler User? @relation("ReportHandler", ...)
  handledAt DateTime?; createdAt DateTime
}
```

## 五、可见性判据（唯一事实来源）

`lib/hall-review.ts` 的 `effectivePublic(hall)` 是公页可见性的**唯一**判据，所有页面/动作都调它，不得在别处手写 `isPublic`：

```ts
function effectivePublic(hall) {
  if (hall.status !== "active") return false;
  if (hall.reviewChannel === "appeal") return !!hall.supplementedAt && !!hall.isPublic;
  return !!hall.isPublic;
}
```

- 公页（`app/(public)/halls/[id]/page.tsx`、`app/(public)/clan/halls/[id]/page.tsx`）：`notFound` 改为"非 owner 且未 effectivePublic 才 404"，owner 始终可见自己的馆（满足 appeal 仅创建者可见）。robots / 分享元数据用有效可见性。
- 后台审核（`app/admin/review/page.tsx` + `actions.ts`）：`reviewHall` 通过时 standard/alternative → `isPublic=true`；appeal → `status=active`、`isPublic=false` 保持。新增「被举报」队列 + `handleHallReport`。

## 八、运营要点

- 后台审核卡片展示：通道、材料清单（类型+编号+图片链接）、关系、脱敏身份证、手机号、申请时间；appeal 额外显示补传截止/是否已补传。
- 补传期限无定时任务，靠 `effectivePublic` 实时判定；owner 控制台横幅显示倒计时，过期自动维持仅创建者可见。
- 举报不直接下架，由人工复核后处置（handled 可结合其他管理动作撤馆/下架）或驳回误报（dismissed）。
