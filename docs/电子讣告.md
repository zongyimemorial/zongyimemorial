# 电子讣告（发布闭环）

> 起因：用户直接问「**用户支付了『电子讣告发布』后，在哪里发布电子讣告？**」
> —— 排查后确认平台**根本没有发布入口**：商品只走完"上架 + 支付"，
> 履约分支没有 `memorial_service` 处理，全仓无讣告页面/API/控制台入口。
> 等于"钱付了、服务拿不到"。同类 `memorial_service` 商品（传记代写 / 纪念视频 /
> 扫码云碑 / 线上追思会 / 墓碑样式 / 官网样式）**同病**。
>
> 本次按"方案 2"补齐完整闭环。

## 1. 产品决策（用户确认）

| 决策项 | 结论 |
|---|---|
| 访问方式 | **公开链接可分享**；发布时**可选**设访问密码 |
| 归属 | **可选**挂在用户名下某座纪念馆（`MemorialHall`）下；不挂则为独立讣告 |
| 审核 | **发布即生效**，无需人工审核 |

## 2. 闭环链路

```
支付购买 / 积分兑换
   ↓  grantObituaryQuota(userId, qty)          ← lib/obituary.ts（两条路共用）
ObituaryQuota { purchased += 1 }
   ↓  控制台 /console/obituaries/new 填表提交
   ↓  consumeObituaryQuota(userId)             ← 条件写扣减（无 TOCTOU）
Obituary { status = "published" }
   ↓
公开缅怀页 /obituary/[id]   （可分享 / 可选密码 / 关联馆入口 / 留言区）
   ↓  控制台 /console/obituaries/[id]
下架（unpublished）/ 重新发布 / 删除
```

## 3. 数据模型

三张表，迁移 `prisma/migrations/20261007000000_add_obituary`。

| 表 | 用途 | 关键点 |
|---|---|---|
| `Obituary` | 讣告主体 | `ownerUserId` 级联删除；`hallId` 可空、`ON DELETE SET NULL`；`passwordHash` 存 bcrypt；`status` 默认 `published` |
| `ObituaryQuota` | **消耗式发布配额** | `userId` **唯一**；只存 `purchased` / `used` |
| `ObituaryMessage` | 缅怀留言 | `userId` 可空（`SET NULL`，允许游客留言后注销） |

### 配额语义

**一次购买/兑换 = 可发布 1 份讣告**（单次服务，非订阅）。
与 `OfferingHolding` 同源的消耗式范式：**购买 increment、使用 decrement**。

剩余份数一律 `purchased - used` **现算**，**不落派生列** ——
落派生列必有一天与真相错位（本仓库反复踩过的"同一个事实两个判据"）。

## 4. 关键技术决策

### 4.1 两条履约路落到同一张表、同一个函数

`lib/pay.ts`（货币支付）与 `app/(public)/points/actions.ts`（积分兑换）
**都调 `grantObituaryQuota`**，因此"花钱买的配额"与"积分换的配额"在控制台完全等价。

⚠️ 判据必须是 `product.type === "memorial_service" && product.slug === "e-obituary"`。
**只判 type 是错的** —— 同类型下还有传记代写 / 纪念视频 / 扫码云碑 /
线上追思会 / 墓碑样式 / 官网样式，只判 type 会让买"追思视频"的用户静默拿到讣告配额。

### 4.2 支付履约分支必须传 `tx`

`simulatePay` 的履约在事务内，`grantObituaryQuota` 必须传
`tx as unknown as Parameters<typeof grantObituaryQuota>[2]`。
用全局 `prisma` 会写到事务外 —— 主事务一回滚就变成"订单没付成、配额却发了"。

### 4.3 扣减用条件写，不用"先查后减"

```ts
updateMany({ where: { userId, used: { lt: row.purchased } }, data: { used: { increment: 1 } } })
```

Prisma 不支持字段间比较，故先读 `purchased` 作上界**常量**，
由数据库行锁保证不超发（与 `consumeOffering` 同构，**无 TOCTOU**）。
用 `count > 0` 判定成功。

### 4.4 密码访问用 HMAC 令牌，**严禁 `node:crypto`**

`lib/share.ts` 的 `createShareToken(pathname, scope)` 把令牌**绑死到具体路径**：
改 id / 改有效期 → 签名失配。解锁走 `POST /api/obituary/[id]/unlock`
→ 校验 bcrypt → 种 `obituary_access` cookie（httpOnly，7 天）。

⚠️⚠️ `lib/share.ts` **整个文件里不能出现 `node:crypto`（包括惰性 import）** ——
middleware 的 import 链会把它带进 Edge bundle，webpack 直接构建失败。详见该文件注释。

### 4.5 访问控制三层

1. `status !== "published"` → `notFound()`（下架即不可见）；
2. 免登录可看（符合"生成链接发给亲友"的承诺）；
3. 设了密码则需持有效令牌。

**SEO**：公开且未加密才可索引；私密/加密一律 `noindex`。

⚠️ `notFound()` 返回的 HTTP 状态码是 **200**，**不要靠状态码判 404**。

## 5. 控制台入口

| 路径 | 内容 |
|---|---|
| `/console/obituaries` | 列表 + 配额概览（`data-obituary-quota`）+ 发布入口 / 无配额引导 |
| `/console/obituaries/new` | 新建（无配额时提交按钮禁用） |
| `/console/obituaries/[id]` | 编辑 + 管理条（查看公开页 / 下架-重新发布 / 删除） |

控制台首页 `/console` 也加了"电子讣告"计数与版块（空态 `data-obituary-empty`）。

**下架与删除都不退还配额**（服务已消耗）；重新发布也不再扣。

## 6. 积分兑换上限（已于 2026-10 后按决策修复）

**问题（已修复）**：原 `lib/points.ts` 的 `REDEEM_SINGLE_LIMIT = 1000`
（`app/(public)/points/actions.ts` 用它拦掉一切 `pointsPrice > 1000` 的商品），
导致电子讣告（`pointsPrice = 2900`）及共 **49 个在售高价商品**在 `/points`
点"兑换"只会得到「超出单次兑换上限」，**永远兑不出来**。该常量按"礼器最高
¥8 = 800 分"定的，之后新增的模板 / 存储包 / 纪念服务从未纳入这条口径。

**已实施的修法（决策第 1 项：日上限 5 万 + 单次不设上限）**：

- `lib/points.ts`：删除 `REDEEM_SINGLE_LIMIT`，`REDEEM_DAILY_LIMIT` 由 1000 提至 **50000**。
  理由：单次上限本意防刷，但积分只能靠消费/签到赚（1 元 = 3 分），攒 5 万分需
  消费约 ¥1.6 万，刷不动；真正需要的护栏是单日累计，5 万可覆盖除最贵容量包
  （storage-50g = 59000 分、storage-500g 更高）外的所有在售商品，容量包需分日兑换。
- `app/(public)/points/actions.ts`：删除单次上限 `if` 块与对应 import；
  兑换按商品自身积分价扣一次分，自然不超过自身价。

> 备注：受影响的三份文档（`docs/存储容量与定价.md`、`docs/空间装修体系.md`、
> `docs/产品体系与定价.md`）原先写明这些商品"开放积分兑换"——修复后终于名副其实。
> 商品页 `/points` 未再对超限商品隐藏兑换提示（不再需要，因为现在真能兑）。

**原待决策的三项（仅留档）**：① 日上限 5 万 + 单次不设上限（✅ 已选）；
② 单次上限抬到 60000；③ 保持 1000 只改文案。
